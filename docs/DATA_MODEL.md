# Data model

## Phase 4F authentication provenance proposal — not applied

Migration 3 supplies binding/challenge/approval references, uniqueness, revisions and recovery but cannot describe an authenticated issuer or ceremony outcome. The [Phase 4F report](IMPLEMENTATION_STATUS_PHASE_04F.md#6-persistence-and-revocation-proposal--no-migration-applied) proposes additive authentication_attempts and append-only authentication_events, with unique challenge ownership, bounded mechanism/issuer/session metadata, sanitized outcomes and links to exact admission audit revisions. No existing approval is backfilled as authenticated.

A new reviewed repository operation would commit provenance, AcceptApproval and reference consumption atomically; two separate ChangeAdmission/external writes are insufficient. Pending/failed/ambiguous attempts receive explicit durable outcomes without fabricating new domain actions. Existing domain revision order remains authoritative; separate ceremony sequence is explicitly linked, not ordered by caller timestamps. No raw credentials, biometric material, OS proof blobs, private input or keys. Actual encodings/constraints and migration require separate approval; SQLite remains migration 3.

## Phase 4E reference trust review — no migration

SQLite remains migration 3; storage/domain formats and canonical vectors are unchanged. Existing challenge/approval/reference uniqueness plus atomic revision/audit enforce one owner, one accepted response and durable ordering. Approval receipt replay is historical, never a fresh authentication proof. Added tests verify wrong manifest/challenge/epoch, expired approval, duplicate/conflicting responses, concurrent response ownership, restart invalidation and rejected private canaries absent from audit bodies. Existing revocation/claim and corruption/restore tests remain in force.

Provider registrations and assessments are in-memory engine code only; no provider table or capability certification is persisted. Principal/evidence fields remain opaque unauthenticated references. The user requires OS-backed authentication; a future reviewed proof/principal representation might need a focused schema proposal, but no migration is necessary or authorized for this milestone. Do not store raw OS proof, keys, credentials, prompts or private inputs in these references. See [ADR-0008](decisions/ADR-0008-provider-and-approval-trust.md).

## Phase 4D schema and transaction decision — before migration implementation

The Phase 4D request authorizes this focused persistence slice. Use migration 3 with three admission tables rather than speculative workflow/provider tables. Existing migration 1/2 text/checksums remain unchanged. This section refines the earlier Phase 4B table proposal using actual Phase 4C aggregate semantics.

- admission_records: admission ID primary key, storage format version, immutable bounded BindingSpec JSON plus canonical binding digest, initial creation/expiry, optional parent-run foreign key, current revision and bounded Snapshot JSON. Binding contains immutable capability references; no raw secret/input fields. Parent references must point to existing runs; no run is fabricated.
- admission_operations: admission foreign key, per-admission consecutive revision (creation is 0), nonzero operation ID, immutable bounded typed request JSON and request digest, immutable resulting Snapshot JSON. Primary key admission/revision and unique admission/operation ID. Creation and each transition append exactly one operation atomically with the projection update. Repository assigns Command.Order from revision, never a caller timestamp.
- admission_references: typed challenge/approval/claim/revocation identity primary key scoped by kind; admission foreign key and operation-revision composite foreign key; unique admission/kind. These are uniqueness/index constraints over the references already in the domain history, not a second domain state machine. One claim per admission and one owner of an attempt ID are enforced by SQLite. Claim/attempt identity remains retained after failed or uncertain outcomes.

Storage JSON is a strict bounded internal envelope, not a public wire format or a change to canonical binding version 1. Reconstruct by NewBinding, New and Apply; compare every audit result, exact revisions, binding digest and final projection. Unknown storage/domain versions, gaps, missing/extra reference rows or mismatches fail closed and preserve data. SQL enforces relationships/uniqueness, not duplicated transition rules. No mutable update/delete API exists for audit/binding/reference rows.

All mutations use the existing nonblocking writer gate and bounded transaction. Compare expected revision inside the transaction before appending; stale callers receive CONFLICT. Same operation ID + identical versioned typed request returns the original recorded receipt (marked replayed), not a new transition or launch permission; same ID with different content conflicts. A different operation ID for a repeated claim/observation/revocation is checked by the domain and rejected. A timeout or ambiguous response requires lookup/retry with the same key; it never proves commit. Commit receipt is historical evidence, not current readiness.

Each open creates a fresh random store-session epoch; admissions can be created/changed only for that session after recovery. Recovery excludes admission writers, rotates epoch, replays/validates all records, applies domain Recover to unclaimed nonterminal states and claimed pending outcomes, and appends recovery evidence transactionally per admission. Failed recovery leaves admission writes disabled. No prior-session record becomes reusable. Existing whole-store integrity/recovery checks remain. Supported backup restoration requires stopping the app and reopening, which establishes a fresh epoch; silent in-place replacement/rollback under a live trusted process cannot be reliably detected and is unsupported. No rollback-resistance or authenticated admission claim is added; positive launches remain unconditionally refused.

Bounds: storage JSON up to 1 MiB for bindings (canonical bytes remain capped at 256 KiB; JSON escaping overhead), 64 KiB operation/result records and at most 64 operations per admission, well above the finite Phase 4C lifecycle. Reads replay one bounded aggregate; recovery pages IDs, not all payloads. No automatic retention or cleanup. A committed migration has no safe down migration: restore a stopped complete backup with the compatible binary, losing later writes and invalidating old admission readiness on reopen. No historical approvals are backfilled. Private input/credential references remain opaque unverified references; no commitment/key algorithm is selected.

## Phase 4B concrete admission migration proposal — not executed

Recommend a relational catalog plus immutable versioned bodies and append-only audit transitions, alongside existing runs/events. Do not overload event-v2 diagnostic strings or the run sandbox label. No event/run/protocol format change is needed for these separate records; future IPC methods still require reviewed negotiation. Proposed next ordered migration (number assigned only when approved; currently migrations 1–2) adds:

| Proposed table        | Minimum keys/body                                                                                                                                                                     | Constraints and role                                                                                                                                       |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| admission_bindings    | id PK, body_version, binding_hash UNIQUE, policy_digest, bounded canonical body                                                                                                       | Immutable sanitized manifest; no raw prompt/credential/environment secrets                                                                                 |
| capability_evidence   | id PK, body_version, digest, provider_id/version, backend/configuration identity, generation, checked/expiry, bounded body                                                            | Immutable evidence snapshots, not trusted merely because stored                                                                                            |
| binding_evidence      | binding_id FK, evidence_id FK, dimension                                                                                                                                              | Composite PK binding/dimension; reject mismatched target/scope in domain validation                                                                        |
| approvals             | id PK, binding_id FK, principal/session scope, challenge identity, engine_epoch, approved/expiry, revocation_generation, body_version                                                 | Immutable approval; one challenge used once; references binding before admission exists                                                                    |
| admissions            | id PK, binding_id FK, approval_id FK UNIQUE, run_id nullable FK, body_version, immutable authorization body, state, revision, engine_epoch, expiry, idempotency_scope/key/body_digest | UNIQUE scoped key; state/revision support compare-and-swap; same key/different body conflicts                                                              |
| launch_attempts       | id PK, admission_id FK UNIQUE, owner_epoch, claimed_at, launch outcome projection, revision, bounded process identity                                                                 | At most one attempt per admission; claim commits before OS call; never reset consumed state                                                                |
| admission_audit       | admission_id FK, sequence, record_version, kind, observation_time, bounded typed evidence                                                                                             | PK admission/sequence, append-only transition/observation evidence; per-admission sequence is audit order, timestamp is not causal order                   |
| admission_revocations | id PK, approval_id nullable FK, evidence_id nullable FK, policy_binding_id nullable FK, generation, reason code, recorded_at                                                          | Exactly one revocation target per row; append-only. Policy revocations reference a binding and apply to its exact policy digest across matching admissions |

A first implementation may combine approval/admission bodies only if it preserves explicit approval identity and revocation; the table set above is the concrete review proposal, not shipped SQL. Use a binding foreign key for policy revocation, then compare its recorded exact policy digest across admissions; no foreign key targets a nonunique digest column. Changing a request identity produces a different exact digest; broader revocation of semantically equivalent restrictions requires a separately reviewed semantic digest and is not inferred. Provider-generation revocation can invalidate evidence by inserting explicit evidence-target revocations; efficient indexed lookup is required before scaling.

All foreign keys use RESTRICT/no cascading history deletion. Enforce IDs/digest syntax, versions, finite states, positive sequence/revision, bounded body sizes and unique claim/approval/challenge constraints. Domain checks additionally bind run/parent ownership, matching scope/digests and expiry. Retain the current single-store lease, WAL/FULL configuration, bounded write gate and deadlines; the lease is not a child isolation boundary. Index admission state/expiry, binding hash, approval/evidence revocation and run references; bounded keyset history reads use audit high water. No long transaction holds a backend call.

Transaction boundaries: preparation stores binding plus evidence associations; approval stores challenge consumption and approval; admission stores authorization body, approval link and first audit transition; claim atomically validates generations, updates admission revision/state, inserts unique attempt/run linkage and appends audit. Post-spawn outcome and audit commit together in a separate transaction. State projections must match the transition log; mismatch blocks further launches and retains evidence. Unknown body versions refuse admission use; unknown database version keeps existing whole-store refusal semantics. Never reinterpret an unsupported version as a permissive legacy request.

Admission expiry is bounded by approval and evidence validity. Reopening the store validates foreign keys, version/digest/state/audit consistency and invalidates prior-epoch prepared admissions. Claimed pending attempts become unknown; original raw events and existing interrupted-run recovery remain untouched. No run is created for a mere refused assessment; run creation/linkage at claim does not assert OS launch. Refused requests may be retained as refused admission records if their sanitized binding validates; malformed inputs yield bounded diagnostic codes, not arbitrary payload capture.

Retention: store bounded redacted metadata and commitments only, within private app data. Retain bindings/approvals/evidence/attempts/audit reachable from admissions and runs; no GC or automatic deletion in this proposal. Immutable means application-level append-only behavior, not protection against a compromised same-user account. A future retention policy must preserve revocation and uncertain-launch evidence. Storage full/unavailable prevents new admission and claims; no in-memory bypass. Audit ingestion failure after a possible spawn stops new admissions and triggers best-effort owned cancellation with uncertainty preserved.

Migration review must include genuine schema-1 and schema-2 fixtures, checksums unchanged, transactional DDL/ledger update, foreign-key checks, upgrade interruption, unknown versions, disk/write failures and byte-for-byte preservation of events/CAS. No historical approvals are backfilled. Stop application and back up the whole private directory before upgrade. Rollback after committed upgrade requires restoring that backup with the old binary and loses subsequent writes; dropping new tables is not a safe downgrade. Restoring a backup must invalidate admissions using a fresh engine epoch so an old prepared record cannot replay. Existing binaries refuse the new schema. No database file, migration source or schema version changes in Phase 4B.

## Proposed Phase 4 relationships and persistence strategy

No table, migration, contract or object format changes in this milestone. Active formats remain event 2 / IPC 1 / run 1 / manifest 1 / SQLite migrations 1–2. This section supersedes earlier unimplemented logical-record and distributed-clock proposals.

| Concept                       | Proposed representation                                                 | Evidence and invariants                                                                                                                 |
| ----------------------------- | ----------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| Workflow                      | First-class small persistent catalog entity, future versioned metadata  | Local ID, created time, human label optional; no private prompt storage by default; grouping does not execute                           |
| Agent run                     | Existing `runs`, not a parallel agent_runs table                        | One adapter execution; workflow membership is a separate versioned association                                                          |
| Event                         | Existing immutable run-scoped event v2                                  | Original IDs, sequence, payload digest and bytes unchanged; workflow discovered by association                                          |
| Participant / adapter         | Workflow metadata and run metadata respectively                         | Role/instance distinct from parser/provider/version; unavailable identity stays unknown                                                 |
| Tool invocation               | Derived projection initially                                            | Existing event refs and observed upstream item ID; no mandatory tool table                                                              |
| Handoff / dependency / parent | Typed provenance-bearing relationship records                           | Endpoints must exist when resolved; optional event evidence must belong to endpoint run; inferred and declared links stay distinguished |
| Workspace state               | Existing committed snapshot + manifest reference                        | Branch workspace is mutable; path alone is not historical state; event association is contextual                                        |
| Evaluation run / result       | Future separate records with immutable evidence/configuration manifests | Judgments reference evidence without changing it; failed/incomplete evaluations remain explicit                                         |

Recommend an incremental catalog migration only after approval: `workflows`, `workflow_runs` (one primary membership per run), and `workflow_relationships` with bounded versioned metadata and immutable revision history. Final SQL, schema number and names remain review items, not a reserved migration 3. Keep workflow-only annotations in catalog records, not fabricated agent events. Policy admission and evaluation storage need separately scoped later migrations; do not create empty candidate tables now.

Use foreign keys to existing runs/events/snapshots and explicit application checks that an evidence event belongs to its claimed run. No cascading evidence deletion. Membership and its provenance/revision commit atomically; relationships commit only with resolved valid endpoints. Store unresolved provider references in bounded pending metadata, and resolve by a new revision preserving the original. For a newly recorded run, a later implementation must atomically create run+membership or keep it explicitly unassigned on failure; never claim a committed relationship before its transaction returns. Reuse the existing bounded writer gate, lease and deadlines, without holding SQL transactions across external execution or CAS writes.

Recovery checks migration checksums/FKs and relationship invariants, retains invalid evidence for diagnosis and blocks affected projections; it does not repair history or infer successful workflows. Evaluation artifacts, when introduced, must publish verified immutable objects before transactional references; interrupted evaluation is marked interrupted and orphan bytes retained, following existing snapshot practice.

Index membership by workflow/run and reverse run lookup; index edges by workflow and endpoint. Paginate catalog metadata with bounded keysets and immutable revision high waters; event queries continue using existing per-run indexes. Limit workflow fan-out and merge buffers; benchmark sparse and large workflows before adding a global materialized event index. Reuse lazy payload reads rather than loading every event to build a graph. Search remains the current bounded sanitized prefix until separately designed.

Migrations remain ordered, checksummed and transactional. Before upgrade, stop all writers and back up the entire private data directory with permissions preserved. Test genuine migration-1 and migration-2 stores, interrupted upgrade, unknown schema refusal and unchanged event/CAS hashes. Old binaries refuse newer databases: additive tables do not imply downgrade compatibility. Rollback means restoring the stopped pre-upgrade backup with a compatible binary, losing later writes; never drop tables to force downgrade. No migration is executed by this design work.

## Implemented Phase 3 records and manifest (2026-10-22)

Migration 2 adds snapshots(id, run FK, optional event FK, optional branch FK, state, manifest hash, typed metadata), branches(id, source-snapshot FK, optional parent FK, origin-run FK, state, typed metadata), objects(hash, size), and snapshot_objects(snapshot FK, object FK). Indexes page snapshots/branches by run and ID. Migration 1 text/checksum remains unchanged; migration order/checksums are validated before advancing. Older engines refuse the newer database; back up the stopped directory before upgrading. Object references commit with snapshot completion and are retained even for damaged snapshots.

Manifest v1 fields: version, policy=portable-ascii-v1, sorted effective relative exclusions, sorted entries, sorted omissions. Entry fields: relative path, file/directory kind, mode and optional hash/length object reference. Omission reason is excluded or symlink. Canonical bytes are the fixed typed JSON field order with sorted arrays, emitted by Manifest.Bytes; no Unicode normalization or newline conversion is performed on file content. Captures use SHA-256 of exact content bytes, superseding the unimplemented domain/kind-prefix proposal below and matching actual Phase 2 hash conventions. Snapshot files/manifests live separately from event payload files under objects/v1/sha256/<64 lowercase hex>.

Paths are printable ASCII only, slash-separated, at most 1024 bytes/64 components and 240 bytes/component. Reject absolute/dot/traversal/empty components, backslashes, control/non-ASCII bytes, Windows device names/reserved characters, trailing dot/space, duplicate paths, case-insensitive collisions, absent/non-directory parents and included default/configured-excluded entries. Unsupported Unicode names fail capture rather than being silently changed. Directories are explicit, including empty ones. File modes are 0600 or 0700 based on executable status; directories are 0700. No timestamps, owner, ACL, xattr, link identity or sparse-allocation preservation is claimed. Symlinks (including broken/cyclic/internal) are omitted and never restored; other special files fail capture. Hardlinked source files are read as bytes and restored separately.

Bounds: 8 MiB/file, 64 MiB included file bytes, 10k visited entries including omissions, 2 MiB encoded manifest and 100 user exclusions. Default exclusions share the existing workspace policy (.git, .codex, .aws, .ssh, dependency/build/cache directories, .env*, *.pem, *.key, credentials/auth.json); explicit policy version plus effective user/storage-root exclusions are persisted. These are declared scope omissions, not unreadable-file success. A failed read, unsupported entry, limit violation or observed change prevents committed publication.

Snapshot states: preparing/committed/failed/damaged. Materialization states: preparing/ready/failed, with kind restore or branch. Source snapshot, optional parent materialization, origin run, workspace and creation time are recorded. Later snapshots carry branch_id; no full event histories are duplicated. Optional event association is contextual and does not assert that later captured bytes were present at that event. Lists use ascending ID keysets, 1..100 rows (UI 50); they are stable for existing records but new random-ID records can require refresh. No complete manifest is sent in a 1 MiB IPC frame; validation occurs inside Go.

## Implemented Phase 2 model and schema (2026-10-22)

This section is authoritative for storage; later proposed tables are future design. Schema migration 1 is embedded in internal/storage/store.go and SHA-256 checked in schema_migrations(version, checksum). It creates:

| Table             | Stored facts and constraints                                                                                                                                                                              |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| runs              | 32-character ID primary key, normalized creation sort key, constrained lifecycle, nonnegative last sequence, typed run-v1 metadata, history integrity and diagnostic                                      |
| events            | Unique ID, run foreign key, positive integer sequence with unique(run_id,sequence), type/time/status/truncation summary, exactly one inline data or object reference, SHA-256/length, bounded search text |
| legacy_imports    | One imported run ID referencing runs                                                                                                                                                                      |
| schema_migrations | Ordered applied versions/checksums; unknown version or changed checksum refuses opening                                                                                                                   |

Indexes support (run_id,sequence), (run_id,kind,sequence) and descending (created,id). SQL always binds user values. New run metadata adds optional adapter, recorder_version, started_at, history (complete/partial/damaged), recovered and diagnostic; existing schema_version=1 remains. Prompts/task text remain intentionally absent. Legacy missing start/version fields are displayed as not recorded.

Event schema_version=2 stays unchanged. Optional payload.truncations lists field, original_bytes and limit_bytes, measured after heuristic redaction and before clipping. Text is limited to 32 KiB plus a visible marker; legacy markers also set the summary truncation flag. Validation caps total serialized event at 256 KiB, validates state, IDs, timestamps, file metadata and collection sizes. Above 8 KiB, the exact event-v2 JSON envelope is stored in payloads/<sha256>.json. This minimal immutable event object is not a snapshot format or full CAS. Detail reads enforce length/digest, strict typed JSON and envelope/index identity. Empty payload means an observed empty payload; unavailable payload is an explicit error.

EventQuery: id, optional kind/search/min/max/cursor, limit 1..100 (default 100). Bounds and sequence strings are canonical nonnegative int64 decimal; event sequences start at 1. Cursor v1 binds run/filter and a captured last sequence. Appends above that high water do not enter later pages. New records must be consecutive; imported gaps are preserved and reported damaged. Returned count is the total persisted event count through high water, not the filtered match count. Search covers at most 1024 bytes of sanitized message + reason + upstream_type using SQLite literal substring/ASCII lower matching; no token syntax, regex, command/output index, Unicode case-folding or external-blob search.

RunQuery: limit/cursor, descending normalized UTC creation + ID; no offset. Concurrent new runs ahead of the cursor appear on refresh, not midway through existing pages. Event/run IDs are validated before queries. Errors distinguish INVALID_ARGUMENT, NOT_FOUND, CONFLICT, STORE_BUSY, STORAGE_ERROR, UNSUPPORTED_SCHEMA, CORRUPT_METADATA, CORRUPT_PAYLOAD and CORRUPT_DATABASE. Responses never include SQL text or raw payloads in error messages.

Historical bootstrap proposals follow. They are retained for context, not current contracts: the logical table list, Lamport clock, domain-prefixed CAS, symlink restoration, automatic cleanup and deferred SQLite driver decision are superseded by ADR-0002 through ADR-0005 and the implemented sections above. Phase 1 staging details at the end describe the legacy importer format only.

## Historical ordering proposal — superseded

Each producer increments its Lamport counter for local events; on receiving a message with L, set `local=max(local,L)+1`. Attach `causes` only to observed message/parent edges. Uninstrumented upstream events have unknown causality; ingestion gets a local sequence, not invented upstream clocks. Stable display sort `(lamport, producer_id, producer_seq)` breaks ties but does not prove causal dependence. P2 serializes ingestion; P6 tests multiple instrumented producers. Overflow is a hard error, never wraparound.

## Historical domain-prefixed CAS proposal — not implemented

Identity: `sha256:<64 lowercase hex>`. Hash exact bytes `chronosync-object-v1\0` + kind ASCII + `\0` + payload bytes. Allowed kinds are a versioned enum (event-payload, file, snapshot-manifest, interaction, fixture-manifest). Include format domain and kind in the hash to avoid cross-type ambiguity. Store at `objects/v1/sha256/ab/<remaining hex>`. No compression in v1; text files preserve original bytes, not newline-normalized content. Manifest JSON uses canonical UTF-8 JSON with lexicographic keys and no insignificant whitespace; file entries sort by normalized relative path. Never hash secret data before redaction when it will be exported as a public fixture.

Write to a private same-filesystem temp file, hash while writing, flush/fsync, atomic publish without overwriting a different object, fsync directory where supported. Verify length and complete digest on reads before returning bytes. Duplicate identity verifies the existing object; mismatch is corruption. SQLite references are committed only after blob durability. Multi-process publication needs a single writer or safe no-replace operation. Filesystem durability details on Windows/macOS are a P2 experiment, not assumed guarantees.

GC marks from retained runs, branches, snapshots, exports and active leases. Sweep unreachable objects only after two completed epochs and a grace period; never race active writes or delete ancestry reachable through a branch. Refcounts may optimize but are not authority. Interrupted writes leave temp files; unreferenced finalized objects are safe orphan candidates, not immediately deleted. Recovery surfaces missing/corrupt referenced objects and blocks restoration.

## Snapshots and Copy-on-Write

Manifest entries contain relative path, file type, mode, size, object ref or symlink target. Capture tracked and explicitly included untracked files; exclude .git, secrets, sockets/devices and oversized files with explicit manifest reasons. Reject unsupported names/case collisions for the destination platform. No dereferencing escaping symlinks. Capture only while agent/writers are paused; record that uncontrolled external writers can invalidate consistency. Verify before/after metadata and retry or reject changed files. A worktree alone does not snapshot dirty/untracked state. Branch shares immutable object refs and writes new objects for changed content; filesystem reflinks are optional optimization, never a requirement. Never hardlink writable branch files to immutable CAS objects. Publish ready branch only after complete materialization; rollback cleans only the owned incomplete branch.

## Migrations and retention

Use ordered SQL migrations with checksums, an explicit schema_migrations table and transaction boundaries. Refuse future schema versions, take a consistent backup for destructive migrations, and never auto-downgrade. Test upgrade from every supported version, interruption, disk full and recovery. Object-format version is separate from DB and event/IPC version; migrate references without mutating existing objects. Retention is user-configured; exports pin dependencies until finished. SQLite driver selection is deferred to P2 (pure-Go portability versus CGO/system SQLite build burden).

## Historical Phase 1 data — retained importer format

`contracts/recorded-event.schema.json`, `contracts/recorder.ts` and `internal/model` define event v2: schema_version=2, random hex event_id/run_id, positive decimal sequence, kind, UTC observed_at, adapter=codex and a typed payload. Payload fields include bounded message/command/output, upstream type/item/thread IDs, optional exit code/state/reason, and optional path/change metadata. Model validation checks version, IDs, sequence bounds/canonical decimal form, UTC timestamp, supported kind/state and serialized size. The JSON schema is structurally checked against actual process output in integration tests; Go is authoritative for semantic bounds. Existing proposed v1 files are retained for review but not emitted or imported. No causal IDs or distributed clock are fabricated.

The root has a process-lifetime advisory `.lock`. Each random run directory contains `run.json` (metadata schema 1) and `events.jsonl`. Lines are `{event,sha256}`; the digest covers Go's compact JSON encoding of the typed event. This is a corruption checksum, not authentication or a CAS object identity. Read revalidates schema/order/identity/digest; malformed lines do not destroy later valid events. An incomplete final line is ignored with a warning. Unknown metadata/event schema is rejected or surfaced as an invalid record; no schema migration runs yet. P2 must import this versioned staging format into SQLite deliberately.

Metadata is written to run.tmp, fsynced, atomically renamed and the directory synced. Each event append is fsynced. Events determine ordinary terminal state; interrupted recovery metadata overrides a nonterminal journal. A hard crash while creating a directory may leave unreadable metadata; listing retains an interrupted placeholder and other histories remain accessible. No power-loss durability certification or full transactional DB semantics is claimed.

Limits: 256 KiB normalized event, 10,000 events and 32 MiB journal per run; adapter stdout line 128 KiB and total stdout/stderr 8 MiB; text fields 32 KiB after redaction. IPC is 1 MiB/frame with pages ≤100 events and approximately 512 KiB event content. Large outputs are not external objects yet: capture truncates bounded text with a marker, and over-budget streams fail. No original prompt or file body is stored. File-change metadata contains relative path, operation and before/after size, SHA-256 and mode for observed files. There are no snapshots, object references, branch records, or migrations implemented.
