# Phase 4F feasibility report — macOS OS-backed authentication

Date: 2026-10-23. Research and design complete; **authentication mechanism remains unselected for production**. LocalAuthentication is a defensible candidate for a separately approved native experiment under the assumptions below. No candidate has yet demonstrated ChronoSync's complete approval boundary. OS-backed authentication remains required; positive policy launch remains refused.

This report is separate from, and does not rewrite, Phase 4A–4E evidence. [Status index](IMPLEMENTATION_STATUS.md). All protocol, persistence and architecture changes below are proposals, not implemented features.

## 1. Audit and scope

The workspace began with uncommitted Phase 4E source and documentation. A SHA-256 baseline was recorded before this work, including untracked files. Those changes are preserved; comparing only with Git HEAD would incorrectly attribute Phase 4E implementation to this phase.

Verified actual code and prior reports:

| Component                                     | Observed authority and limitation                                                                                                                                                                                                                                 |
| --------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `internal/policy/registry.go`                 | Closed production registration wraps ConservativeProvider; unknown/advisory evidence only. Registry generation checks do not authenticate a person.                                                                                                               |
| `internal/supervisor/policy.go`, `process.go` | Every non-nil policy returns PolicyError before process setup. No receipt consumer. Legacy nil-policy execution remains available and is not policy-verified.                                                                                                     |
| `internal/admission`                          | Canonical manifest v1, challenge/binding/epoch/expiry checks and reference-state transitions. PrincipalReference and ExternalValidation are not authenticators.                                                                                                   |
| `internal/storage/admissions.go`              | Migration 3, one challenge/approval/claim reference per aggregate, atomic revision/audit, idempotent historical receipts, replay validation and conservative recovery. No authenticated proof provenance or authentication-attempt lifecycle.                     |
| `internal/ipc/server.go`                      | Strict envelope/run.start decoding; no approval/provider/admission operation. Arbitrary renderer success flags cannot enter a trusted approval route because none exists.                                                                                         |
| Rust `main.rs`, `bridge.rs`                   | Typed commands; bundled engine launched over inherited stdio; transport handshake/version checks, not peer code-identity authentication. Bridge timeout is ordinarily 15 seconds; an interactive ceremony cannot be bolted onto this synchronous exchange safely. |
| React `App.tsx`                               | Consent resets on input changes; no OS authentication or native trusted manifest display. A compromised renderer remains untrusted.                                                                                                                               |
| Packaging                                     | Tauri bundle disabled in checked-in config; no explicit authentication deployment floor, native LA dependency, peer-authenticated channel or reviewed release signing/entitlements in the configuration. A local build is not signed-distribution evidence.       |

The engine must create and retain the challenge, recompute binding/freshness and commit approval. A native trusted component must own the OS context and receive its callback. The renderer may request intent only; it must neither receive a reusable authentication capability nor forward an authoritative result. OS authentication does not establish filesystem/network enforcement, executable authenticity or trusted private-input commitments.

## 2. Authoritative evidence and candidate comparison

Apple documentation was consulted on 2026-10-23; links accompany claims. “Documented” below means the API contract, not demonstrated ChronoSync behavior. API pages sometimes returned JavaScript shells; search-indexed Apple documentation and installed Apple SDK headers supplied readable content. Markdown links from those shells failed in the web reader with unsupported content-type; no claim relies solely on an unreadable page.

### LocalAuthentication / LAContext

`deviceOwnerAuthentication` permits the macOS device-owner authentication mechanisms described by Apple, including Touch ID, Apple Watch and the user's password. It does not identify a particular fingerprint or certify that a person read an execution manifest. Password/Watch acceptance must be an explicit product decision, not an assumed biometric-only guarantee. [Apple: deviceOwnerAuthentication](https://developer.apple.com/documentation/LocalAuthentication/LAPolicy/deviceOwnerAuthentication).

`evaluatePolicy` supplies a Boolean/error callback to the calling process, on a framework queue; localizedReason is app-provided display text. It supplies no signed nonce or manifest assertion. Our inference: only a trusted callback owner can associate that result with an engine challenge; receiving the same Boolean over renderer IPC establishes nothing. Configuration profiles and policy/device differences can affect interaction. [Apple: evaluatePolicy](https://developer.apple.com/documentation/LocalAuthentication/LAContext/evaluatePolicy%28_:localizedReason:reply:%29).

`canEvaluatePolicy` checks prerequisites and its result can change. It is not authentication and must not become a cached grant. [Apple: canEvaluatePolicy](https://developer.apple.com/documentation/localauthentication/lacontext/canevaluatepolicy%28_:error:%29).

For a proposed fresh ceremony: allocate a new context for each challenge, explicitly keep Touch ID reuse duration zero, never share a successful context across challenges, and invalidate it on terminal results. Apple documents zero as disabling reuse of recent biometric device unlock. This addresses that documented reuse path, not every possible OS/profile caching behavior; fresh interaction must be tested on each supported policy/OS. [Apple: reuse duration](https://developer.apple.com/documentation/LocalAuthentication/LAContext/touchIDAuthenticationAllowableReuseDuration).

Biometric-only policy refuses when biometrics are unavailable, unenrolled or locked out; its fallback button is not permission to silently switch to another policy. This could meet a stricter factor choice, but excludes Macs/users lacking usable Touch ID. Account authentication is broader. Apple SDK LAContext.h corroborates these policy distinctions and availability; no hardware capability was queried here. [Apple: biometric policy](https://developer.apple.com/documentation/localauthentication/lapolicy/deviceownerauthenticationwithbiometrics).

Cancellation, authentication failure, system interruption, unavailable/unenrolled/locked-out biometrics, invalid context and noninteractive execution must all deny approval. Application invalidation during evaluation yields appCancel. A late successful callback after an engine deadline/revocation must still be discarded. No callback is a wall-clock or restart-resistant proof. [Apple: LA error cases](https://developer.apple.com/documentation/localauthentication/laerror-swift.struct/appcancel).

### Keychain access controls and Secure Enclave operations

Keychain access control gates access to an item; `userPresence` and `biometryCurrentSet` have different semantics. The latter invalidates access on biometric enrollment changes. Reading an item is not automatically a challenge signature or proof of manifest consent. Freshness requires context/access-control policy design and native validation, not simply creating an item once. [Apple: userPresence](https://developer.apple.com/documentation/security/secaccesscontrolcreateflags/userpresence), [Apple: biometryCurrentSet](https://developer.apple.com/documentation/security/secaccesscontrolcreateflags/biometrycurrentset).

An authentication-gated Secure Enclave key operation could sign canonical challenge bytes for verification by the engine. Apple documents hardware-bound private-key operations; this is materially different from an LA success callback. It still requires trusted key enrollment, verifier key pinning, caller access restrictions, freshness, rotation/revocation and recovery. A compromised authorized caller can request the wrong bytes, and a signature is not proof the user saw them. Key management is excluded in this phase; no key is created or selected. [Apple: protecting keys with the Secure Enclave](https://developer.apple.com/documentation/Security/protecting-keys-with-the-secure-enclave).

On macOS, file-based and data-protection keychains differ. A future design must choose explicitly rather than borrow iOS assumptions. Access groups depend on code-signing entitlements; restricted entitlement claims require appropriate provisioning. No private keychain content or credentials were inspected. [Apple: TN3137](https://developer.apple.com/documentation/Technotes/tn3137-on-mac-keychains), [Apple: distribution signing](https://developer.apple.com/documentation/xcode/creating-distribution-signed-code-for-the-mac/).

### LARight / LAPersistedRight

LARight groups authorization requirements; persisted rights add a Secure Enclave-backed key. Apple demonstrates authorizing a persisted right and signing a challenge. This can supply verifiable bytes, but introduces the same enrollment, storage and revocation decisions as a direct key design. Reusing an authorized right is not assumed to provide a new ceremony for each admission. It is a candidate for later key-backed research, not a shortcut around the key-management exclusion. [Apple: LAPersistedRight](https://developer.apple.com/documentation/localauthentication/lapersistedright), [Apple: local authorization flows](https://developer.apple.com/videos/play/wwdc2022/10108/).

### Authorization Services

Authorization Services evaluates rights using the Security Server and can authenticate when necessary; credential/right reuse means a request need not produce a new authentication dialog. Externalizing an authorization reference does not bind it to ChronoSync's canonical manifest. Apple states the API is not supported inside App Sandbox. Custom authorization-database rules, privilege helpers and escalation are unnecessary for this feature and outside scope. It is not recommended for the initial candidate. [Apple: Authorization Services](https://developer.apple.com/documentation/Security/authorization-services), [Apple: authorization concepts](https://developer.apple.com/library/archive/documentation/Security/Conceptual/authorization_concepts/02authconcepts/authconcepts.html) (archived conceptual source, not current packaging certification).

| Candidate                       | OS assertion                                          | Operation freshness / binding                                                               | Feasibility position                                                                |
| ------------------------------- | ----------------------------------------------------- | ------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| LAContext account policy        | OS policy evaluation, with allowed factors            | New context plus engine challenge/deadline; callback only, binding enforced by trusted code | Smallest candidate for a native experiment, subject to factor and trust assumptions |
| LAContext biometric-only        | Successful allowed biometric policy                   | Same callback limitation; explicit refusal if unavailable; no automatic password downgrade  | Candidate if biometric-only requirement is approved                                 |
| Keychain ACL / SecKey operation | Item/key access under OS access control               | Signing can bind bytes; reading an item alone cannot                                        | Deferred: requires key/provenance lifecycle and platform testing                    |
| LARight / persisted right       | Authorization state; persisted variant protects a key | Authorized key can sign challenge; right reuse needs review                                 | Deferred: more lifecycle state, macOS 13+ API surface                               |
| Authorization Services          | Right granted under configured system policy          | Rights/credentials may be reused; not a manifest assertion                                  | Poor fit; do not alter authorization database or add privilege helper               |

No candidate protects a compromised engine or establishes rollback-resistant approval by itself. If the requirement includes a cryptographically transferable OS assertion, plain LAContext is insufficient. If it includes protection from a compromised application/administrator, none is established by this review. Those are blockers, not reasons to weaken OS authentication.

## 3. Threat model and residual risk

Classifications describe the proposed architecture under an uncompromised OS, signed native host and engine. They are design analysis, not adversarial test results.

| Attacker                                             | Prevent / mitigate / cannot defend                                                                               | Required boundary and residual risk                                                                                                                                                                                                        |
| ---------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Malicious webpage outside the app                    | Prevent direct approval ingress by design; mitigate prompting abuse                                              | No remote command origin or auth-result endpoint; CSP and origin/capability rules remain. Page social engineering and native-host bugs remain.                                                                                             |
| Compromised renderer / forged IPC                    | Prevent self-issued success; mitigate misleading consent                                                         | Native host fetches/display engine-owned summary independently and owns callback; renderer can request intent but never submit a result. Prompt flooding and user confusion need rate limits; native compromise is not renderer isolation. |
| Another same-user process                            | Mitigate impersonation, not full account compromise                                                              | Mutual code-identity checks, private session-bound channel and hardened signed components required. Same-user files/DB manipulation, accessibility abuse, injected code or stolen account credentials are not solved by LA.                |
| Replaced local executable                            | Mitigate app/engine substitution with peer/signature verification; cannot authenticate an arbitrary agent binary | Pinned identity/version policy and release validation required. Agent path/artifact checks still need a separate launch-binding backend. A version-shaped CLI response is not authenticity.                                                |
| Replay of prior result                               | Prevent within intact live coordinator                                                                           | Exact nonce/admission/manifest/epoch/session tuple, one active attempt and atomic consumption. Neither a callback Boolean nor an old receipt is a new grant.                                                                               |
| Database modification / old backup                   | Detect structural inconsistency; invalidate stopped restored sessions; cannot prevent coherent live rollback     | Read replay, uniqueness and new epoch on reopen remain. No trusted external rollback anchor exists.                                                                                                                                        |
| Administrator/root controlling trusted components/OS | Cannot defend within this design                                                                                 | Hardware key properties do not prove correctness of a compromised verifier, UI or launch coordinator. No elevated security guarantee.                                                                                                      |
| Compromised app binary or engine                     | Cannot defend                                                                                                    | Trusted code could change displayed bytes, associate success with another challenge or bypass checks. Application binding is not independent attestation.                                                                                  |

Principal semantics remain narrow: OS device-owner policy was satisfied in the trusted local session. An LA callback does not provide an independently verified civil identity, specific biometric identity, or authenticated UID claim to another process. An engine-generated opaque principal reference may identify the verified native session only after channel identity is established; it is bookkeeping, not the authenticator. Whether this principal model is acceptable requires explicit sign-off.

## 4. Execution location and conditional recommendation

| Placement                       | Callback owner and delivery to engine                                                                             | Trade-offs and crash behavior                                                                                                                                                                                                                    |
| ------------------------------- | ----------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Existing Rust/Tauri native host | Native code receives LA callback; separate private authenticated native-to-engine channel sends correlated result | Reuses UI process for trusted summary/prompt lifecycle; keeps secrets out of React. Existing renderer-callable command route and stdio request interface are insufficient for authoritative results. Host crash cancels/invalidate pending work. |
| Go-engine-owned native boundary | Engine-owned platform bridge receives callback directly; no success message crosses host IPC                      | Reduces proof transport but requires native interoperability/UI lifecycle in the engine, changes build/portability conventions and may need a trusted summary UI anyway. A CLI process is not automatically a trusted GUI authenticator.         |
| Narrow native helper            | Signed helper receives LA result, speaks peer-authenticated bounded channel to engine                             | Isolates code and may avoid trusting a renderer-adjacent host, but adds packaging, lifecycle, UI ownership and mutual identity verification. Root helper is neither needed nor authorized. Helper crash means unknown/denied, not retry success. |

Recommend **existing Rust native host as the smallest experiment**, with LAContext and an engine-owned challenge, only if trusting that native host is accepted. Keep authentication logic outside renderer command payloads. No generic `complete(success)` command. A dedicated private XPC boundary with mutual code-signing requirements is the preferred transport design to investigate; Go interoperability remains unresolved. If safe interoperability requires a helper or native engine bridge, return with a focused architecture/dependency proposal rather than smuggling results through public stdio.

Apple documents enforcing peer code-signing requirements on NSXPCConnection; the local SDK marks this API macOS 13+. A requirement must pin intended signing authority and code identifier, with reviewed version/update rules, not merely UID, PID, path or any signed binary. Mutual verification, listener/client roles and session binding require testing; code signing does not mean a legitimate peer's request is semantically authorized. [Apple: XPC peer requirements](https://developer.apple.com/documentation/foundation/nsxpcconnection/setcodesigningrequirement%28_:%29).

This recommendation is conditional, **not a selected production authentication mechanism**. A serialized LA success on a correctly authenticated channel is a trusted host statement, not a cryptographically transferable Apple assertion. If that trust model is rejected, explore key-backed challenge signatures under separate authorization.

## 5. Proposed approval protocol — not implemented

1. Engine creates an immutable canonical binding and new admission identity under its current random epoch. Secure private inputs/object identity must already be resolvable; otherwise no production approval-ready state. Generate a unique challenge, authentication-attempt ID and native-session correlation ID. Persist IssueChallenge before presenting anything.
2. Engine retains the tuple `(protocol version, admission ID, challenge ID, canonical binding digest, engine epoch, native session ID, attempt ID, policy choice, expiry)`. Proposed initial ceremony deadline: at most 60 seconds, bounded by admission/evidence expiry, measured with a monotonic in-process timer as well as persisted wall times. This is a reviewable choice, not a current default or trusted global clock.
3. Native host accepts a challenge only over the verified engine channel. It fetches canonical bytes/summary from that channel and displays exact public executable/argv/workspace/policy information using native text controls, never renderer-provided HTML. Truncation must not conceal the action being approved. The OS localized reason identifies the operation concisely but is not a trusted digest display or cryptographic binding.
4. Host creates a fresh LAContext for that tuple, with zero reuse interval. Native code calls OS evaluation; React never sees a context, proof or authoritative success. Preflight availability is not approval. Do not collect passwords, biometric templates or application-provided credentials. Policy fallback is only whatever the explicitly approved policy permits.
5. Callback is handled on a serialized native coordinator; match the exact still-pending tuple. Invalidate context and erase transient result on cancellation, disconnect, expiry, error or terminal completion. Native host sends a bounded result on the private authenticated channel, once. Engine rechecks channel/session, pending attempt, binding, engine epoch, expiry, revocation and expected revision. Caller-provided timestamps are never authoritative.
6. Engine commits the successful provenance record, AcceptApproval domain transition, challenge consumption and all associated audit entries in one transaction. No two-step “approval first, provenance later” write. Response comes after commit. One-time uniqueness plus revision comparison decides competing responses. No actual launch follows.
7. Denial, user/system cancellation, lockout, unavailability, timeout, unknown callback and ambiguous transport refuse. Close the challenge via an appropriate terminal transition and preserve a sanitized attempt result. No automatic prompt retry or silent policy fallback. Reattempt requires a new admission/challenge under this single-challenge domain model; do not relax it implicitly.
8. Exact retry of a **known committed** operation may return its historical receipt for reconciliation; it never authorizes another attempt. A lost callback before commit creates no approval. A lost commit response requires query/retry of the same operation, never another authentication-to-launch assumption. This distinction resolves ambiguity without treating a timeout as success or rollback.
9. Revocation/cancellation and approval serialize under the same coordinator/repository revision discipline. Before approval, Refuse/Expire prevents acceptance. After approval, Revoke invalidates it; claim remains separately controlled and unused in this phase. A late callback loses the race. After any host/engine restart or channel replacement, invalidate all pending tuples; rotate/revalidate engine epoch and require a fresh native session. Do not restore callback state from SQLite.

This protocol proposes new internal native transport and eventually a public **intent-only** operation. Both require separately reviewed bounded typed contracts and negotiation before implementation. There is no new public method, token or authentication capability advertisement now. A trusted engine can still misbind an OS result; application correlation cannot defend against compromise of its own verifier.

## 6. Persistence and revocation proposal — no migration applied

Migration 3 already retains Challenge ID/binding/epoch/issued/expiry, ApprovalReference ID/principal/evidence digest/times, immutable binding and unique typed references. Per-admission audit revisions serialize transitions and receipt retries. Its missing facts are authentication mechanism/profile, native issuer provenance, ceremony attempt and sanitized failures/ambiguity. Do not overload PrincipalReference or EvidenceDigest with raw proof material or silently label all existing approvals authenticated.

Propose a future additive migration (number assigned only after approval), with two small tables:

| Record                    | Proposed columns / constraints                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| ------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `authentication_attempts` | Attempt ID PK; admission ID FK and unique challenge ID linked to the recorded IssueChallenge; version; immutable binding digest/engine epoch/native session reference; mechanism/profile version and requested LA policy; reviewed issuer code-identity/profile reference; created/deadline times; revisioned terminal outcome; optional unique approval reference ID and completion operation ID. One ceremony per challenge. No raw credentials, OS blobs, username, biometric data or localized error strings. |
| `authentication_events`   | Attempt FK; per-attempt sequence PK; operation ID unique per attempt; bounded versioned outcome/static reason and engine observation time; optional admission domain revision FK to `admission_operations(admission_id, revision)` when the same transaction changes domain state. Append-only application API, retained on failure.                                                                                                                                                                              |

The attempt table binds the existing challenge reference and admission together; migration/application validation must reject cross-admission references. Proposed outcomes: pending, approved, denied, cancelled, unavailable, expired, revoked, ambiguous, interrupted. Approved requires a matching approval reference and domain revision from the same commit. Terminal retries return the recorded result; changed operation content conflicts. Mechanism/issuer metadata remains a historical engine assertion, not re-verifiable OS proof. Its public metadata digest may correlate with existing EvidenceDigest; no private commitment algorithm is selected.

Use a new reviewed repository operation to apply domain transition and authentication provenance in the **same existing writer-gated transaction**. The current exported ChangeAdmission alone cannot do this atomically with an external second write. Authentication start/outcome events need their own sequence; do not invent unsupported admission actions to inflate domain audit. Per-attempt sequences order ceremony events; admission revisions continue to order domain transitions, with explicit linkage rather than timestamps implying causality.

Recover pending attempts as interrupted/ambiguous without granting approval; preserve already committed evidence but invalidate prior-session unclaimed admissions as today. Host disconnection invalidates its outstanding attempts even if the engine survives. Revocation after commit remains append-only and never deletes history. Duplicate success concurrent with revocation has one serialized order; a revoked challenge cannot become approved afterward. Old rows have no authentication metadata and remain unauthenticated, never backfilled. Future migrations must retain old checksums/history, reject unsupported versions and test stopped-backup restoration. Live coherent rollback remains unsupported.

Schema proposal is deliberately not SQL executed in this phase. Actual constraints, versioned encodings/bounds and principal/issuer profile must be approved before migration. If key-backed proof is chosen instead, return with a different focused schema/key-lifecycle proposal; do not add keys to these tables by convenience.

## 7. Platform support and packaging gates

Read-only installed Apple SDK header inspection found: LAContext evaluation API macOS 10.10+, account policy/invalidate 10.11+, reuse property 10.12+, biometric policy 10.12.2+, LARight/LAPersistedRight and NSXPCConnection peer requirement 13.0+. These are SDK availability annotations, not an application support claim. Apple documentation also lists newer companion policies; do not assume one policy's behavior remains identical across OS versions.

Propose macOS ARM64 **13+ as the experiment floor** if the documented NSXPCConnection API is used. No minimum macOS version is explicitly pinned in current Tauri config, and no runtime support matrix has been validated. Test the chosen minimum release plus each intended supported major release on real hardware, including Macs without usable Touch ID and accessory disconnects. SDK 26.5 syntax success does not prove execution on macOS 13, 14, 15 or 26. Intel, Windows and Linux authentication remain out of this review's implementation scope.

Required before production: reviewed native LA/Foundation bindings; explicit deployment floor; native window/run-loop ownership; code signing of host/engine/helper as applicable; hardened runtime with minimal exceptions; peer identity/profile checks; packaging and update validation; and distributed-artifact tests. Apple describes hardened runtime as mitigating classes of injection/tampering, and notarization requires it. Neither is human authentication or universal same-user protection. [Apple: hardened runtime](https://developer.apple.com/documentation/Security/hardened-runtime), [Apple: notarization issues](https://developer.apple.com/documentation/security/resolving-common-notarization-issues).

No privileged helper or security-settings change is proposed. Basic LA evaluation does not justify adding Keychain sharing entitlements or an App Sandbox claim. Exact entitlements and Info.plist requirements must be audited for the selected APIs/distribution route; Face ID usage documentation must not be misread as evidence that this macOS Touch ID path is configured correctly. [Apple: LAContext configuration](https://developer.apple.com/documentation/localauthentication/lacontext). If Keychain groups are later chosen, their provisioning/access rules require a separate review. No signing identity, private credential or provisioning secret was read here.

No tests in this phase establish biometric authentication, OS factor freshness, same-user attack resistance, trusted signing/packaging, secure manifest display, or cross-version compatibility. No intentionally induced biometric lockout, credential access, native prompt or privileged experiment was run.

## 10. Decisions and exact next approval

| Decision                             | Position after feasibility review                                                                                                                                      |
| ------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| OS-backed requirement                | Unchanged and mandatory; checkbox/local-intent-only fallback rejected                                                                                                  |
| Mechanism                            | Unselected for production; LAContext is first experiment candidate, not certified approval                                                                             |
| Factor policy / principal            | Decide whether OS account policy including password/Watch is acceptable or biometric-only is required; accept/reject trusted-session device-owner semantics explicitly |

| Same-user / root / engine compromise | Conditional mitigations only; root/engine compromise and live DB rollback not defended                                                                                 |

Next authorization should be **an isolated, non-production native experiment**: select factor policy and trust assumptions; approve a macOS 13+ ARM64 target matrix, Rust/native API binding approach and peer-authenticated host/engine transport prototype; use a disposable non-secret manifest; verify fresh interaction, cancellation, timeout, session restart, manifest mismatch and forged peer/result rejection. Do not connect it to actual admissions or processes, store keys, change system settings, or add public commands/migrations. Interactive authentication requires the user's presence and explicit test scheduling. If dependencies are needed, present them before installation.

Only after that evidence and security review should a separate request approve the production handler, typed intent/private transport contracts and persistence migration. Positive policy launch, sandbox backend and receipt consumption remain separate later approvals. Phase 1–3 native GUI acceptance remains unverified/blocked. Stop here; no authentication integration or commit/push is performed.
