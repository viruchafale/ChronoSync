# Security model

## Phase 4G isolated protocol model — native boundary blocked

The [Phase 4G experiment report](IMPLEMENTATION_STATUS_PHASE_04G.md) distinguishes deterministic protocol results from OS authentication and peer identity. The separate standard-library test module has no production imports, store, process launcher, exported entry point or native call. Its successful peer verifier exists only in tests; nil/unverified peers refuse. No test outcome can authorize a production admission.

Read-only inspection found the existing host/engine executables ad-hoc signed without team identity/internal requirements, and no native XPC route. A compiled LocalAuthentication binding, reviewed fixture packaging/signing profile and explicit account-versus-biometric policy remain approval gates. No ordinary local channel, UID/PID or verification Boolean replaces peer authentication. Production conservative provider and supervisor refusal remain unchanged; no same-user/admin resistance or native authentication is established.

## Phase 4F macOS authentication feasibility — design only

OS-backed authentication remains required. No production mechanism is selected. Apple's LAContext is a candidate for an isolated experiment: the trusted native process receives a policy result, not a signed manifest assertion. Availability checks, a recent device unlock, an IPC Boolean or a stored digest are not a new approval. The complete source-backed candidate comparison and threat matrix are in the [Phase 4F feasibility report](IMPLEMENTATION_STATUS_PHASE_04F.md).

Conditional design trusts the signed native host and engine, keeps the renderer outside result authority, binds a fresh ceremony to one engine challenge/manifest/epoch/session, and requires a reviewed private peer-authenticated channel. The current inherited stdio bridge does not establish peer code identity. Native display must use engine-owned content, independently of React. Same-user impersonation mitigations depend on actual signing/channel tests; account/OS/native-process compromise, administrator control and coherent live rollback remain outside established guarantees.

OS device-owner authentication is not verified civil identity or proof the user understood the manifest. Account password/Watch versus biometric-only factor policy and acceptable principal semantics remain explicit decisions. No fallback to checkbox consent. Keychain/Secure Enclave signing would require a separate key lifecycle and verifier trust decision, not a Boolean upgrade. No native prompt, key access, backend or security-settings change occurred.

## Phase 4E verified authority inventory

The user requires OS-backed authentication for future approval. No such mechanism is implemented; local consent, database approval references and verification booleans cannot satisfy it. Positive policy-based launch remains refused. [ADR-0008](decisions/ADR-0008-provider-and-approval-trust.md) records the implemented registry and the blocked authentication decision.

Public metadata is limited to reviewed non-secret argv/path descriptions, identifiers, environment names/rules and evidence references. No raw prompt, stdin, credential or environment value is added to durable admission data. Existing legacy prompt transport is still private stdin and is not admission persistence. A secret hidden in a public argument cannot be detected reliably; approved non-secret input provenance remains a future coordinator responsibility. Private-reference commitments cannot be considered production-ready without an approved algorithm/key lifecycle. No such coordinator, key system or positive-ready result is introduced.

Provider errors and rejected IPC requests return static messages, excluding raw private input and provider diagnostics. Synthetic canary tests check rejected inputs do not reach recorder storage or admission operation rows; this is not a universal secret detector. Approval reference tests cover exact binding, expiry, duplicates, concurrent responses, unique challenge ownership and restart. Existing claim/revoke, corruption and stopped-restore tests remain authoritative for persistence, never authentication.

## Phase 4D durable-state boundary

Migration 3 persists only the internal admission model's bounded public launch descriptors and opaque approval/capability/private-input references. No credentials, environment values, stdin/private prompts or commitment keys are collected; no new commitment algorithm is selected. A public argv/path must already be reviewed as non-secret: storage cannot recognize a secret disguised as public text. Unused command fields are rejected rather than retained. Existing private-directory/lease/WAL/FULL and parameterized-query controls apply.

Database constraints and transactionally generated revisions establish one accepted claim/history transition under concurrent repository callers, not a trustworthy human approval or OS launch. Synthetic external_validation references may be stored for domain tests and are never promoted to production capability authority. Read replay detects invalid/corrupt state but hashes do not authenticate it against a compromised OS user. Unknown versions, broken references or failed recovery refuse further admission mutation/opening as applicable; evidence is retained, not repaired or deleted.

Recovery invalidates prior-session readiness and preserves consumed unknown outcomes. Reopening a stopped restored backup creates a fresh epoch. Silent in-place rollback/replacement under a live process, copied memory/epoch or an attacker rewriting DB/history coherently cannot be made safe by these records; those operations remain unsupported. This milestone provides no trusted rollback detector, and the entire positive-launch boundary remains closed. Required trust/authentication/credential/backend decisions must be resolved before any receipt can be considered for execution.

## Phase 4C internal contracts only

Phase 4C models external approval/evidence/input references without authenticating them. Unresolved object identity blocks modeled readiness; external_reference and external_validation are not production trust claims. Caller epochs/times/order do not prove freshness, durable consumption or rollback resistance. No positive admission, key-management mechanism or backend is introduced. See the [Phase 4C report](IMPLEMENTATION_STATUS_PHASE_04C.md) and [canonical specification](SYSTEM_DESIGN.md).

## Phase 4B proposed admission trust boundary

The trusted Go engine owns policy validation, launch planning, provider registration, evidence verification, binding construction, approval/admission records and final supervisor decisions. The installed Rust host is the local UI/engine transport boundary; frontend messages are untrusted intent. No capability object, effective policy, approval timestamp, actor identity, evidence expiry or verified flag supplied by the renderer becomes authority.

| Value                            | Allowed origin and IPC treatment                                                                                                  | Engine responsibility                                                                                                                                                   |
| -------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Requested policy / launch inputs | User or explicitly authorized internal caller; proposed typed bounded IPC request                                                 | Validate every restriction and reconstruct exact adapter launch plan; reject unknown fields/versions, no implicit legacy fallback                                       |
| Capability evidence              | Registered trusted in-process provider/backend only; never incoming renderer JSON                                                 | Verify provider/build/configuration provenance, scope, fresh generation and backend-bound handles; a hash/boolean is insufficient                                       |
| Human approval                   | User action observed through a reviewed trusted-host confirmation route; IPC carries challenge response, not self-issued approval | Bind fresh one-use challenge to engine summary and local session/actor scope; persist grant, expiry/revocation. Principal authentication strength remains a review gate |
| Effective policy                 | Engine resolver only                                                                                                              | Recompute from trusted evidence; renderer receives read-only bounded summaries                                                                                          |
| Admission record                 | Engine repository only                                                                                                            | Allocate identity, commit immutable authorization and enforce compare-and-swap/one-use constraints                                                                      |
| Launch request                   | Host/internal caller can request consumption by admission ID and idempotency key                                                  | ID is not a bearer permission; verify caller/session scope, actual binding, freshness/revocation, durable claim and backend prerequisites                               |

Keep ConservativeProvider unchanged. Current synthetic test evidence must never be registered as a production provider, persisted as production certification or injected through a plugin/IPC. Future provider registration requires code review, trusted distribution/version identity and backend-specific adversarial evidence. A subprocess provider would need an authenticated private channel and an explicit authority design before use; no generic external plugin trust is assumed. Evidence issuance must bind the exact backend context used to launch, not a separate successful probe on an unrelated context.

Readiness is not immutable: OS configuration, credentials, workspace and executable paths can change. A trusted provider must expose revalidation and invalidation/generation semantics, not merely the existing Capabilities slice. Backend mechanisms must bind checked objects and controls at launch where required. Approvals cannot waive an unsupported mandatory policy. The current engine still cannot guarantee filesystem/network/resource/credential containment, detached-process cleanup, atomic workspace state or race-free path-based launch.

Local approval is not proof against a compromised renderer or malicious same-user process. Decide whether trusted native confirmation or stronger OS authentication is required before shipping a human-approval claim. Source prompts and credentials must not be persisted or logged as launch bindings; public unsalted hashes can reveal guessable secrets. Proposed ephemeral keyed commitments and opaque broker versions require an approved key lifecycle and invalidate admission after restart/key loss. No key/secret machinery is implemented here.

Revocation prevents launches only when ordered before final authorization; later requests become cancellation with observed results. Hostile OS/root and compromised trusted engine remain outside this local application's trust boundary. Database integrity checks detect corruption, not attacker-proof audit history. See [protocol/failure windows](SYSTEM_DESIGN.md) and [migration proposal](DATA_MODEL.md).

## Phase 4A established guarantee and limits

The implemented pure resolver refuses unknown, unsupported, unavailable, unverified, expired, mismatched or merely observed requirements. The conservative provider asserts no host guarantees. Supervisor policy requests are refused before process setup; it cannot accept injected positive evidence. Nil-policy legacy Codex launches are unchanged and must not be represented as evaluated. This establishes decision/refusal logic only, not filesystem/network/credential/resource containment. Positive evidence is synthetic in tests, not authenticated by a verification boolean or hash.

See [Phase 4A status](IMPLEMENTATION_STATUS_PHASE_04A.md) for exact scope, contract semantics, verification and remaining gates. Earlier Phase 4 sections below describe the original design milestone; proposed backends and positive admission remain unimplemented.

## Phase 4 requested policy and enforcement design — unimplemented

Threat extension: an agent, tool, repository hook or evaluator may intentionally seek credentials, host sockets, historical source, external paths, unrestricted descendants or network egress. Workflow correlation is untrusted data, not an authority to launch. Keep the trusted engine/store outside the child boundary. Current same-user file permissions and upstream Codex flags do not establish that boundary.

Four separate versioned records are proposed:

1. **RequestedPolicy**: immutable ID/version/digest; canonical workspace identity; each dimension's allowed set/limit and required enforcement level; workflow ceiling reference and run-specific selections. Omitted security dimensions default to denied or unresolved, never unrestricted. Explicit allow-all is itself an approval-sensitive choice.
2. **EnforcementCapability**: platform/kernel/backend/version/configuration identity; dimension, scope and level (`enforced`, `observed`, `advisory`, `unsupported`, `unknown`); dependency/privilege requirements; probe evidence/version/time and known escape limits. Implementation status and enforcement level are separate axes. An upstream declaration is not a verified capability.
3. **EffectivePolicy**: resolved dimension-by-dimension restrictions, enforcing mechanism and evidence references, remaining uncertainty, admission decision and request/capability digests. Required `enforced` cannot be satisfied by `observed`. This record is created before launch; execution results do not retroactively establish it.
4. **PolicyObservation**: run/admission reference, timestamp, dimension, observed denial/violation or uncertainty, sanitized evidence and source, detection coverage and action. No detected violation means only no detection. A monitoring gap produces uncertainty, not compliance.

| Policy dimension              | Requested rule and required evidence                                                                                                               | Failure / limitation                                                                                                 |
| ----------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| Workspace and external files  | Canonical read/write roots, explicit denied roots and temporary space; backend validates actual child access including symlink/mount/reparse cases | Engine os.Root only constrains engine operations; read-only workspace says nothing about other paths                 |
| Network                       | Deny/all/explicit destinations and scope including DNS, IPv4/IPv6 and local endpoints                                                              | Proxy settings and provider flags alone cannot satisfy enforced deny; destination filtering remains backend research |
| Child processes               | Allowed launch scope, descendant boundary and lifetime; adversarial subprocess tests                                                               | Process group membership is not filesystem isolation and detached descendants may escape cleanup                     |
| Environment and credentials   | Explicit environment names; minimal synthetic home; credential access grants by purpose, never secret values in audit                              | Allowlisting environment does not prevent reading HOME, credential stores or inherited handles                       |
| Host services / local sockets | Deny host sockets, named pipes, agents, daemon interfaces and inherited descriptors unless explicitly granted                                      | Denying internet does not deny local privileged services; test separately                                            |
| Resources / duration          | CPU, memory, disk, process count, output and wall time as separate hard or observed limits                                                         | Existing output/time bounds do not enforce CPU/memory/disk; measurement after use can overshoot                      |
| Cancellation / descendants    | Grace and hard-stop expectations, owned boundary identity and cleanup evidence                                                                     | Report unknown survivors on backend/engine crash; never claim cleanup from stale PIDs                                |
| External filesystem changes   | Deny child writes outside approved roots; separately observe selected changes                                                                      | Before/after scanning cannot attribute external writers or detect all transient edits                                |
| CAS and historical data       | Child cannot access app data, DB, snapshots or unrelated runs; expose only approved materialized inputs                                            | Same-user 0700/0400 permissions alone cannot enforce this against that user's child                                  |
| Human approval                | Request/effective policy/backend/workspace/executable identities and expiration bound to approval                                                  | Consent UI is not containment; changed identity or widened access invalidates approval                               |
| Audit                         | Persist sanitized admission and observation evidence before claiming action; retain failures and unknowns                                          | Audit failure prevents new admission; running capture failure cancels with cleanup uncertainty if needed             |

Resolution is fail closed: any required unsupported/unknown dimension yields a typed refusal listing unmet dimensions and evidence gaps. Never launch then discover whether required controls work. A user may explicitly request a weaker policy only where product rules allow it; show changed protections, create a new request/digest and fresh approval, and label the execution accordingly. This is not a silent downgrade of the rejected request. Workflow defaults cannot widen a run; effective permissions must fit the workflow ceiling. Mandatory product restrictions cannot be overridden by a checkbox. Exact mandatory restrictions and approval persistence need review before implementation.

## Implemented Phase 3 controls and limitations (2026-10-22)

Snapshot capture introduces persistent source bytes and requires separate explicit consent. Files excluded by the shared sensitive-name policy and configured paths are not read. Remaining file bytes are stored exactly; redacting their contents would make faithful restore impossible. Secrets in ordinary source files may therefore be retained. No encryption, upload, command execution, Git invocation or full secret detection is added. Default exclusions and limitations are visible before consent.

ASCII path validation/collision rejection, explicit directory parents, os.Root containment, non-following/nonblocking POSIX file opens, per-read identity checks, bounded directory batches and per-operation byte/entry/deadline limits protect engine-mediated operations. All symlinks are omitted; special files fail. Object directories are created through an already owned root and symlinked directory entries are refused. CAS files publish read-only to the owner (0400), use no-replace linking within CAS, and are validated by digest/length before reuse/read. The same bytes never become a writable hardlink in a branch. Same-user malicious races, alternate mounts and hostile OS storage remain outside this boundary; two scans are not a security sandbox or atomic snapshot.

Restore can create only random owned destinations under private managed-workspaces. Existing paths and a changed symlinked managed root are refused. Source projects and their Git metadata are never overwritten. A failed materialization is kept with failed state for inspection. Inventory never deletes anything; all snapshot/branch references, unreferenced objects and temp evidence remain protected from automatic GC. This consumes disk and requires a future reviewed retention/cleanup design. Windows storage/ACL/runtime support is blocked; actual power-loss/disk-full/fsync fault guarantees and cross-platform runtime behavior remain unverified.

## Implemented Phase 2 storage boundary (2026-10-22)

The application-data root must be a real private directory (0700); DB/lease/payload files are 0600 and existing unsafe database sidecar paths are rejected. The lease excludes another engine. Payload names are generated SHA-256 identifiers, validated again on read, and opened through os.Root; arbitrary stored paths are never opened or executed. SQLite receives bound parameters and trusted_schema=OFF. Event data is validated before persistence and again before detail rendering; React renders text, not HTML. Summary rows contain type/time/status/truncation flags, not command output or source text.

Payload redaction remains heuristic. The sanitized diagnostic search prefix is additional retained private data; neither it nor the database is encrypted. Prompts are not stored. Errors report operation/code without SQL, filesystem locations or raw vendor data. No recordings are uploaded. This does not stop an attacker running as the same OS user from manipulating application data, racing SQLite paths or reading plaintext; filesystem permissions are not a sandbox.

Retained legacy journals, orphan objects and payloads consume disk indefinitely until a future explicit retention design. Back up with the application stopped by copying the entire private directory, preserving permissions; never copy a live DB alone or place WAL on network storage. Unknown migrations and structural corruption fail closed without destructive repair. Missing payloads are not fabricated. Recovery annotates unfinished runs and never claims stale process cleanup succeeded. Native Windows ACL/runtime support and actual disk-full/power-loss/fsync failure testing remain unverified. See [evidence and remaining gates](IMPLEMENTATION_STATUS.md).

Status: threat model plus implemented Phase 1 controls below. ChronoSync can now spawn explicitly authorized Codex executions; it has no engine network service or generic Tauri shell/filesystem plugin. Strong OS isolation is not implemented.

## Threats and trust boundaries

Assume prompts, repositories, generated code, tool output, imported fixtures and provider events are malicious. Protect source files, credentials, original Git history, private recorded data, and host resources. Trust the installed app/engine and OS only within the documented boundary. A compromised user account/root process is outside the local-store confidentiality guarantee. A renderer compromise must not obtain arbitrary command execution through host IPC.

| Boundary                   | Required controls                                                               | Residual risk                                             |
| -------------------------- | ------------------------------------------------------------------------------- | --------------------------------------------------------- |
| UI → host                  | narrow typed commands, CSP, no remote navigation, capability checks             | host implementation bugs                                  |
| Host → engine              | absolute bundled binary, inherited private pipes, frame limits, protocol checks | malicious replacement binary; signing deferred            |
| Engine → agent             | consent, allowlisted environment, owned working root, process-tree policy       | upstream behavior and policy drift                        |
| Agent → filesystem/network | future verified OS/backend policy, not currently implemented                    | worktrees/path checks alone do not constrain subprocesses |
| Capture → storage/export   | pre-storage redaction, private permissions, explicit export                     | heuristics can miss secrets                               |
| Import → renderer/restore  | schema/hash/size/path validation, text rendering                                | archive bombs, symlink and TOCTOU attacks                 |

## Future consent and data-handling requirements

Consent records exact workspace, adapter, allowed access, network policy and budgets; policy widening requires new consent. Never read credentials to display them. Let Codex own authentication; forward only required environment, not the entire host environment. Private app-data dirs use 0700/files 0600 on POSIX and equivalent per-user ACLs on Windows. Local encryption at rest is not implemented; relying on OS account permissions/disk encryption must be disclosed. Redaction policy removes credential headers, tokens, configured secret patterns and denied files before persistent capture. Default raw sensitive capture is off; uncertain payloads can be omitted with a reason. Redaction is imperfect, so export requires inspection and records omitted fields; a redacted request may no longer be replayable. Diagnostic logs must not echo prompts, environment, or raw stderr wholesale.

## Future workspace/VFS requirements

Use platform-aware absolute path normalization, reject NUL, traversal, device paths and unsupported encodings; resolve allowed roots before use. Match full path components, not string prefixes. Restrict temp directories to per-run owned locations. Reject symlink escapes and unsafe hardlinks; descriptor-relative no-follow operations and revalidation mitigate TOCTOU. Windows reparse points, UNC paths, drive-relative paths, reserved names and case folding need dedicated tests. A userspace VFS protects only engine-mediated operations. Arbitrary child commands require OS isolation to enforce equivalent policy. Never claim these path checks secure the host.

Worktree creation is explicit, with a registry of owned roots, IDs and leases. Do not delete by glob or trust an unvalidated marker file alone. On cleanup verify ownership and repository worktree registration, refuse user changes unless separately approved, never prune unrelated worktrees or modify original HEAD/index. Recovery lists stranded workspaces for review.

## Historical isolation roadmap — superseded by Phase 4 matrix

The initial roadmap favored disposable read-only execution. Actual P1 supports explicitly consented read-only or workspace-write in the selected workspace; enforcement remains upstream/OS dependent. P4 evaluates Linux namespaces/seccomp or optional containers, Windows restricted tokens/job objects and supported sandbox, and supported macOS OS isolation. Job objects/process groups bound lifetimes, not filesystem access. Where a required capability cannot be enforced, block execution rather than silently degrade. Container availability and network namespaces are not universal.

## External-interaction recording

P5 first controls explicit adapter/test-tool transport boundaries. Record method, canonical target, selected headers, body hash/ref, response status/body, timing and correlation after redaction; require scope and consent. A loopback proxy is optional with per-run authentication, origin restrictions, destination allowlist and no public bind. HTTP CONNECT does not reveal encrypted bodies. Do not install a root CA or intercept provider TLS implicitly. Proxy bypass, QUIC, direct sockets, subprocesses ignoring proxy variables, certificate pinning, remote MCP and provider internals remain unsupported unless tested under enforced egress policy. Unknown interactions invalidate a whole-run replay claim. Replay blocks network, rejects unmatched/ambiguous requests and never falls back to live services without a separate user action.

## Abuse and resource controls

Cap frame size, total captured bytes, object sizes, decompression ratios, recursion, fixture counts and query pages. Redact before error reporting. Deadline is mandatory; process-tree cleanup must be tested on each enabled OS. AST checks are advisory heuristics unless a configured policy explicitly blocks an operation; they are not malware detection. Threat-model reviews and adversarial tests are release gates in every phase.

## Implemented Phase 1 controls and deviations

The UI requires consent for the exact entered workspace/task/executable/policy/timeout; changes reset the checkbox. Engine validates consent and specification independently. The executable path is a trusted user choice; a version-shaped response cannot authenticate a binary. Project config/rules/hooks remain subject to Codex trust behavior. No shell interpolation or bypass flags are used. HOME/USER/TMPDIR/LANG/LC_ALL/CODEX_HOME are the only inherited variables; a fixed installation PATH and NO_COLOR are supplied. A selected workspace-write policy edits the user's selected directory directly—no hidden worktree or repository-history mutation is performed by ChronoSync.

Recorder files are private POSIX 0600 under a 0700 directory. Store operations and inspection use Go os.Root; scanning skips symlinks, checks opened identity, and never intentionally reads outside its root. Defaults exclude .git/.codex/.aws/.ssh, .env*, _.pem/_.key, credentials/auth.json, dependencies, caches and common build outputs; configured relative exclusions are supported. It hashes regular files only, ≤1 MiB each and ≤64 MiB total, with a 20,000-entry limit. Same-user races, hardlinks, mount behavior and external concurrent writers remain limitations; this is not a VFS jail. All symlinks are skipped, including safe internal ones.

Prompts are not persisted. Captured strings are redacted for common credentials/private-key patterns and length bounded. Unknown/malformed vendor bodies are omitted. Arbitrary private code or novel secret formats can remain in known outputs; local encryption and complete secret detection are absent. stderr is bounded and redacted before persistence; the native bridge suppresses raw engine stderr rather than leaking it into renderer logs. Events render as text, never HTML.

macOS/Linux group cleanup is tested locally on macOS, including an ordinary grandchild. It does not constrain files/network/resources or reliably kill detached sessions after an engine SIGKILL. Windows recording/storage are blocked rather than using insecure fallbacks. Engine EOF and explicit cancellation are tested; native process crash/power-loss cleanup and full GUI close behavior remain unverified. Store lock prevents simultaneous writers, but no adversarial multi-user confidentiality guarantee or encrypted storage is claimed.

No network interception, external-response replay, seed control, worktree restoration, AST enforcement or confirmed-deadlock detection exists in Phase 1. The future sections above remain roadmap requirements.
