# System design

## Phase 4G experimental coordinator — no production wiring

A standalone module under experiments/macos-auth-protocol models a single synthetic display-only challenge and terminal observation. Coordinator-generated IDs, manifest digest, epoch/native session, policy label and bounded deadline form the exact tuple. Canonical messages are bounded to 4096 bytes; replay/mismatch/malformed/late/duplicate callbacks refuse. An out-of-band verifier seam is test-only and has no native implementation. No production API or data format changes.

The [Phase 4G report](IMPLEMENTATION_STATUS_PHASE_04G.md) supplies the pending native interface and fixture/dependency/signing proposal. A future native host would receive the OS callback; an isolated coordinator would validate the peer and tuple. Current production stdio and React do not carry authentication results. Native binding/packaging approval and explicit factor choice precede implementation.

## Phase 4F proposed authentication ownership

The [Phase 4F report](IMPLEMENTATION_STATUS_PHASE_04F.md) compares Rust native host, engine-owned native interoperability and a narrow helper. Conditional smallest experiment: Rust host owns fresh LocalAuthentication context and native manifest display; Go owns canonical challenge, expiry/revocation checks and one-time durable commit. The renderer requests intent only. A dedicated mutually authenticated native/engine channel must be proven; no authoritative result may be sent through a generic renderer-callable command. Current synchronous bridge timeouts are not an interactive ceremony design.

Proposed tuple includes protocol, admission/challenge/binding/epoch/native-session/attempt IDs, policy and deadline. Reject changed, cancelled, expired, revoked, ambiguous or replayed results. Exact committed retries may reconcile a historical receipt only. Restart/channel loss invalidates pending tuples. Proposed authentication provenance and admission approval commit together in one repository transaction. No LA API, public method, channel, callback consumer or migration is implemented. Mechanism selection awaits native evidence; every policy-controlled launch still refuses.

## Phase 4E provider and approval boundary

ProviderRegistry in internal/policy has a closed production constructor and no registration or serialized evidence input. RegisteredProvider supplies versioned identity, exact target/scope, bounded capabilities and a current revocable generation. Registry.Resolve validates intent, takes detached copies, acquires evidence, matches provenance, rechecks generation and uses engine time for the unchanged pure resolver. The only production implementation wraps ConservativeProvider; it reports unknown/advisory. Registry errors are static typed ProviderError codes. Supervisor diagnostic assessment now uses the registry; unconditional pre-process PolicyError refusal remains.

Go IPC envelope/run.start decoding now rejects unknown fields, duplicate case-equivalent keys, trailing bodies, malformed types and oversized inputs. Existing frame limit and recorder semantic validation remain. No new protocol command or field exists, and valid legacy requests remain compatible. Rust and React are unchanged. Other historical query decoders are not claimed hardened by this change.

OS-backed authentication is an explicit user requirement. No trusted approval handler, external_validation producer or positive readiness coordinator exists. Existing admission.New/Apply and migration 3 remain unchanged. The proposed authenticated challenge/response/cancel/revoke/restart contract and exact decision gate are in [ADR-0008](decisions/ADR-0008-provider-and-approval-trust.md). Strong authentication, private-input commitments and rollback protection are not implemented; synthetic references are never promoted to authority.

## Phase 4D implemented admission repository — no execution integration

Storage now implements AdmissionRepository with CreateAdmission, ChangeAdmission, GetAdmission, AdmissionEpoch and RecoverAdmissions. Records are internal only; no IPC/UI command or supervisor consumer was added. Domain NewBinding/New/Apply remain unchanged and are the sole canonicalization/transition authority. Storage version 1 is separate from domain version 1; SQLite advances to migration 3.

Creation commits immutable binding/initial state, revision-0 audit and projection together. A transition validates its expected revision inside the existing writer-gated SQL transaction, assigns Command.Order = expected revision + 1, invokes Apply, updates the projection with a conditional revision predicate, appends the operation/result and inserts any challenge/approval/claim/revocation uniqueness row. Commit failure rolls back all changes. SQL uniqueness prevents two claim IDs for one admission and reuse of an attempt ID for another admission. The storage shape rejects irrelevant command fields, so ignored fields cannot become a private-data storage channel. Failed domain transitions are not committed; a caller must explicitly submit a legal Refuse or ObserveNotStarted/ObserveUnknown transition to record a refused assessment or unsuccessful final-validation outcome. There is no automatic transition invented by storage.

Same admission/operation ID and identical canonical typed request returns the original receipt with Replayed=true, even after later transitions or restart. That receipt is historical, not current readiness or a second claim. A different body (including expected revision/time/identities) under the same key is CONFLICT. A new operation ID with stale revision conflicts; a fresh revision repeating an illegal terminal action is ADMISSION_TRANSITION. Creation uses expected revision -1 internally; caller Command.Order must be zero. Per-admission revision/audit order is generated transactionally; caller timestamps remain observations only. Cancellation, writer backpressure, SQL failures or ambiguous commit responses do not prove commit; retry the same operation identity or inspect GetAdmission rather than generate a new launch attempt.

Reads run in a bounded read transaction and replay the complete bounded aggregate from creation through domain transitions, comparing binding digest, every result, final projection and exact reference rows. Typed canonical JSON equality rejects duplicate/unknown keys and ambiguous encodings. Unknown storage versions fail with UNSUPPORTED_SCHEMA; invalid domain/body/history relationships fail closed. No snapshot hydration bypass or second SQL state machine is introduced. GetAdmission returns bounded state/history summaries; no arbitrary SQL or raw command body API is exposed.

Open applies the checksum-ledger migration, imports legacy history as before, then performs admission recovery before returning the store. Recovery obtains exclusive admission coordination, disables mutation, rotates a randomly generated session epoch and validates integrity/FKs plus each aggregate. It pages IDs in groups of 100, then applies/commits domain Recover per relevant admission. Unclaimed nonterminal states become invalidated; claimed pending becomes outcome_unknown and retains its attempt identity. Previously conclusive/unknown outcomes and terminal unclaimed records are not rewritten. Recovery is repeatable; if interrupted, completed invalidations remain and the next open resumes validation of all records. Failure leaves admission writes disabled and evidence intact. Existing run/snapshot recovery stays separate and no process is resumed or killed.

A mutation from a prior session is refused regardless of persisted timestamps. A deterministic exact retry may retrieve its historical receipt without reactivating it. Recovery uses max(current time, previous observation time) solely for conservative invalidation/unknown transitions; it cannot renew approval. Epochs are fresh random identities, not trusted monotonic counters. Stopped backup restore plus reopen invalidates old readiness; restoring/replacing an active DB in place is unsupported and cannot be reliably detected. There is no rollback-resistance or authenticated approval guarantee. No process path consumes a repository receipt, and the supervisor still refuses every policy-controlled launch.

## Phase 4C implemented internal binding and transition contracts

`engine/internal/admission` implements pure domain values only. It does not resolve policy, authenticate approval, discover identities, read clocks, persist state or launch. Policy dimensions/Target/Outcome are reused from internal/policy. Phase 4A supervisor refusal is unchanged. A modeled prepared or claimed value is not a durable record or authorization token.

### Canonical binding version 1

NewBinding validates and copies the input, sorts only environment/evidence collections, then stores private canonical bytes and hash. Spec and Bytes return detached copies. No decoder, IPC schema or storage format is added. The SHA-256 input is exactly the following sequence:

1. Literal ASCII domain `chronosync-launch-binding` followed by one NUL byte; unsigned 32-bit big-endian version 1.
2. Length-prefixed strings: admission ID, engine epoch ID, adapter, adapter version, adapter configuration digest.
3. Executable object: path, artifact digest, object-reference digest (empty only for unresolved identity), identity-status string.
4. Unsigned 32-bit argument count, then each argument string in exact original order, including empty arguments.
5. Unsigned 32-bit environment count; entries sorted by ASCII name, each encoding name, rule string, external reference ID, value-rule version digest.
6. Input kind, external reference ID, commitment digest; kind none requires the latter two strings empty. Private-reference input requires both references, but no commitment generation occurs here.
7. Working-directory object and workspace object, each in the same four-field order as executable; unsigned 64-bit workspace generation; workspace-state digest, policy-request digest, effective-restrictions digest.
8. Target platform, backend, backend version, configuration digest.
9. Unsigned 32-bit backend-evidence count; entries sorted by dimension string, each encoding dimension, evidence ID, digest, provider label, unsigned 64-bit generation, valid-from and valid-until milliseconds as unsigned 64-bit values after positive int64 validation.
10. Optional parent-run ID as a string; empty explicitly means absent. No workflow identity is invented.

Every string is an unsigned 32-bit big-endian byte length followed by exactly those UTF-8 bytes. IDs and digests are encoded as their validated lowercase hex text, not decoded bytes. No BOM, whitespace padding, terminator, normalization, host path cleanup or locale conversion is applied. Fixed string fields and counts determine boundaries. Nil and empty collections both encode count zero. No maps or floating point values occur. Unknown versions reject rather than produce future-version bytes. EvidenceDigest uses the separate domain `chronosync-admission-evidence` plus NUL followed by the 64 ASCII characters of the binding hash; this commits to the evidence set and the rest of its binding, not to provider authenticity. Phase 4A policy hashing is unchanged.

### Validation and bounds

IDs/epochs are nonzero 128-bit lowercase hex identities supplied by the caller; digests are 256-bit lowercase hex. Labels use the existing policy 1–64 ASCII identifier grammar. Environment names use its uppercase-name grammar and limit of 64 entries. Evidence includes exactly one entry for each existing policy dimension except human_approval/audit, which would be self-referential at binding creation; those are validated later through external assessment/approval references. Duplicate dimension/evidence IDs or environment names reject. Environment order is irrelevant; argument order and empty elements are significant.

New domain bounds are: 128 arguments, 32 KiB per argument, 1,024-byte path spellings and 256 KiB total canonical bytes. These are bounded internal proposals implemented under Phase 4C's explicit canonicalization scope, **not new launch/OS limits**. The 32 KiB and 256 KiB limits align with existing bounded recorder text/event budgets; 1,024 bytes matches the snapshot path budget; 128 argv entries conservatively bounds a newly modeled list (the current Codex adapter uses far fewer). Total-size validation caps aggregate data; no OS command-line capacity is assumed. Generations must be positive uint64; evidence times are positive int64 milliseconds with strictly increasing validity interval. No default expiry/TTL is selected; callers must supply it.

Paths are syntax-checked only: absolute slash paths for darwin/linux; uppercase drive:/ paths for windows. Reject NUL/control bytes, invalid UTF-8, backslash, empty/dot/dot-dot components and trailing slash except a root; Windows additionally rejects reserved device names/characters/trailing dot or space. UNC/device/drive-relative forms are not supported by this initial contract. No path is resolved, renamed or checked on disk; conversion to a native path and safe object binding remain backend decisions. Argument UTF-8 bytes are preserved, including controls other than NUL; no shell is invoked. Unicode equivalent spellings remain byte-distinct.

Environment has no value field: public-configuration or private references identify external exact-value rules by ID/version digest. Input has none or private-reference plus external commitment. No raw environment secret or stdin content is accepted, hashed or stored by these types. Public argv/path strings must be supplied only from reviewed non-secret inputs; the package cannot detect a credential disguised as public text. Secret-bearing argv is unsupported. The external commitment algorithm, key lifecycle, credential broker and authentication scheme remain unresolved: Phase 4C only holds their references and cannot validate their security.

Object identity is explicitly unresolved or external_reference, never verified. Unresolved objects are representable and hashed with their limitation but block modeled readiness. External_reference asserts only that a reference exists; actual backend verification is an external prerequisite. Artifact/workspace hashes do not close replacement or writer races.

### Pure state semantics

New creates preparing with explicit creation/expiry times. IssueChallenge → awaiting_approval binds ID/epoch/hash/interval. AcceptApproval → approved records a matching external approval reference with principal/evidence reference and expiry bounded by the challenge; it does not authenticate a human. Prepare → prepared requires a matching external assessment, current evidence and external approval-validation result. Claim → claimed fixes a valid attempt ID once. FinalValidate and BeginAttempt each recheck readiness; BeginAttempt is a modeled intent only and can occur once. Separate observations set not_started, started (only after modeled attempt), or outcome_unknown. An unknown outcome is never inferred to be no-start or changed to started by this initial model.

Checks bind assessment outcome, request/effective digests, exact binding/evidence-generation digest, approval ID and validity interval. They are internal untrusted-by-default references: only an explicitly supplied external_validation marker exercises the successful domain path; no producer of authoritative validation exists. These values must never become frontend assertions or a replacement policy resolver. No production readiness is established by constructing them.

Each successful Apply returns a new value with strictly increasing explicit order and nondecreasing explicit time; failure returns the unchanged prior value and a typed static error. Refuse/Expire/invalidation are terminal for unclaimed records. Revoke before claim invalidates; after claim it prevents further validation/attempt and records cancellation required when an attempt may exist, without changing known outcome. Recover with a different epoch invalidates unclaimed states and turns a pending claimed outcome into unknown, never reusable. Already conclusive outcomes are not rewritten by recovery. Repeated terminal observations, unknown state/version, duplicate claims and stale order reject.

This models sequencing only. Two callers evaluating the same prepared value can each compute a claim; future SQLite compare-and-swap/unique constraints must decide the sole accepted transition. No memory counter is durable order. Rejected readiness does not itself persist invalidation: a future coordinator must record refusal/revocation/expiry as appropriate and never use a stale value after error. No global challenge registry or one-use approval store is implemented.

NewEpoch validates a supplied nonzero ID; it does not generate randomness or a monotonic epoch. A future trusted engine must allocate a fresh identity on start, replacement, restore or loss of trusted state, and invalidate prior references. The package cannot detect a silently restored database or reused caller epoch and claims no rollback resistance. Clock rollback rejects a transition rather than inventing trustworthy time. Backend revocation, human-authentication strength and private commitment mechanisms remain approval gates.

## Phase 4B proposed admission protocol — not implemented

A policy assessment answers whether supplied evidence satisfies restrictions. Admission additionally binds approval, identity, freshness and durable one-time launch intent. Phase 4A does not implement admission: all non-nil supervisor policies refuse; nil-policy Codex launches remain legacy. The protocol below must not be attached to that legacy path without separate approval.

### Identity and lifecycle

Engine-generated random 128-bit hex IDs identify an admission and its single launch attempt separately from a run ID. Client idempotency keys are scoped to a trusted host session and operation; they are not authorization tokens. Repeat the same key/body to retrieve the same result; conflicting bodies refuse. Retrieving an ID never authorizes a second spawn.

1. **Prepare binding, no launch:** validate policy and bounded execution input; trusted adapter builds exact launch configuration. Engine captures workspace/executable/backend identities and obtains trusted capability evidence. Record a proposed immutable binding manifest and evidence bundle. Unsupported or unknown mandatory restrictions refuse; preparation is not an approved or satisfied admission.
2. **Approve exact binding:** host displays the engine-generated summary and a fresh one-use challenge. The engine records local approval with binding hash, evidence-generation set, session/principal scope, expiry and revocation epoch. A bare frontend boolean is insufficient. Approval identity means an observed local action through the trusted host, not verified physical-human identity; compromised renderer/host resistance requires a separately chosen confirmation mechanism.
3. **Commit prepared admission:** recheck approval, policy and evidence. Resolve all dimensions and durably store an immutable authorization body with mutable state `prepared`, in one transaction with evidence references and an audit transition. Acknowledgement follows successful commit only. Prepared means eligible for an attempt, never that a process exists.
4. **Claim once:** under an engine launch/revocation coordinator, validate the actual retained launch inputs and backend context again. In one bounded transaction, compare-and-swap `prepared` to `claimed`, consume the one-use approval, insert the unique attempt with owner engine epoch, bind/create the run metadata if needed, and append the audit entry. Check expiry/revocation generations within that transaction. Commit must be known successful before proceeding. No SQL transaction spans the OS call.
5. **Final check and OS attempt:** while retaining the coordinator and backend-bound handles/context, revalidate volatile evidence, deadlines and revocation generation immediately before the backend operation. Failure after claim consumes the admission permanently and records `not_started` if no OS attempt occurred. Otherwise make at most one spawn call. There is no implicit retry, fallback backend or promotion of legacy execution.
6. **Record observation:** on definite spawn error with proof no child exists, persist `not_started`; on observed process creation, persist `started` and scoped process identity (backend handle/token, boot identity and creation identity, not PID alone). An adapter-completed turn remains distinct from process creation. Subsequent process exit belongs to existing run lifecycle; the attempt records only launch evidence and diagnostics. Ambiguous backend errors become `outcome_unknown`.
7. **Recovery:** expire/invalidate unclaimed prepared admissions from a prior engine epoch; never resume them automatically. Any claimed attempt without conclusive durable outcome is `outcome_unknown`, consumed forever. Backend-specific retained identity may permit a later append-only reconciliation observation; absence of a process now does not prove it never started. Never kill/relaunch from a stored PID alone. Existing run recovery remains interrupted/cleanup-unverified as applicable.

Admission terminal states before claim are `refused`, `expired`, `invalidated`; `claimed` means irrevocably consumed, including a failed/no-start attempt. Launch outcome is a separate dimension: `pending`, `not_started`, `started`, `outcome_unknown`. Unknown may receive later evidence but cannot become reusable. No automatic admission recycling after timeout or error.

### Avoid circular approval and audit evidence

Phase 4A requires human_approval and audit evidence but its current provider cannot supply either. Preparation therefore computes a binding before final Resolve; it must not emit a fake satisfied result. The binding includes requested restrictions, prospective exact effective restriction set and backend evidence generations, excluding its own future approval/admission digest. Approval refers to that binding. The trusted approval provider verifies a previously committed approval; the audit provider attests storage service readiness/guarantees, **not the existence of a future commit**. The admission transaction separately establishes actual durable authorization; the claim transaction separately establishes actual consumption. A success boolean from either transaction cannot be substituted for verified backend enforcement. Final Resolve result and all evidence refs are recorded alongside the binding, without self-referential hashes. Changes to the binding or backend evidence generation require a new approval. Workflow ceilings and optional approvals remain unsupported rather than bypassing the mandatory dimensions.

### Unavoidable crash and revocation windows

SQLite and process creation are not atomic. A crash after claim commit but before the OS call leaves an indistinguishable durable prefix from a crash just after child creation. Recovery must report uncertainty unless stronger backend evidence exists. This design offers at most one attempted spawn per admission through the coordinator, **not exactly-once execution or guaranteed eventual launch**. Choosing permanent consumption sacrifices availability to prevent replay. A rolled-back claim cannot authorize launch. An ambiguous commit response causes no OS call and requires reconciliation; a caller must not retry the spawn based on an assumed rollback.

Revocation and launch claims serialize through the same coordinator. A revocation acknowledged before final launch authorization blocks the attempt; a request arriving while that critical section is in progress may be ordered after spawn and must be reported as revocation/cancellation of active work, not “never launched.” External backend revocation and filesystem changes cannot be serialized by a Go mutex: a backend must bind/check them atomically enough for its advertised guarantee, or admission must refuse. A deadline is the earliest of approval, evidence and admission expiry, with monotonic checks during one engine epoch. Wall-clock rollback or uncertain boot/epoch freshness invalidates readiness; no fresh authorization is inferred from persisted timestamps.

If outcome persistence fails after spawn, immediately stop new admissions and request cancellation through the owned backend handle; preserve uncertainty if cancellation or storage fails. Do not claim rollback undoes an OS launch. No unrelated source files or historical objects are cleaned up as recovery.

### Launch-binding contract proposal

Use a separately versioned canonical `LaunchBinding` manifest; Phase 4A's request digest currently hashes ordered Go JSON policy fields only and does not cover argv, environment, stdin, adapter or actual filesystem identities. Preserve that digest as `policy_request_digest` with its algorithm/version; do not silently redefine it. A new domain-separated binding hash covers length-delimited typed fields in a specified order, bounded integers and explicit absence markers. Freeze encoding vectors before implementation; no map iteration, shell-joined strings, locale normalization or Unicode renaming. A semantic restrictions digest may exclude the request ID, but is distinct from that existing request-identity digest.

Retain open executable/directory identities where supported; future backend APIs must establish that the checked objects are the launched objects. Ordinary portable os/exec path-based launch does not supply that guarantee. A post-launch digest or PID check detects some changes too late. Managed copied workspaces and signed binaries can help but neither alone proves confinement. If an approved backend cannot prevent substitution or describe its weaker guarantee honestly, refuse the required policy.

Credentials are injected only from a trusted broker and approved reference/version, never persisted values. Exact secret/argv/stdin comparison needs a keyed commitment or immutable broker version bound to the same engine epoch; loss of the key invalidates admission rather than reconstructing a secret hash. Key protection/rotation and credential grants remain approval gates. This milestone neither collects secrets nor changes current Codex HOME/CODEX_HOME handling. Portable fields describe intent; backend handles, atomic object binding, credential confinement, secure process cleanup and external-writer exclusion are platform-specific unimplemented guarantees.

## Phase 4A resolution and refusal boundary

Resolve validates explicit mandatory dimensions, exact target/scope/restrictions and verified current enforcement evidence. It takes evaluation time as input and returns detached evidence, established dimensions and structured refusal reasons. Requirements satisfied is not launch authorization. Production supervisor policy requests always refuse before exec/pipe setup; no trusted backend or durable approval/audit exists. Legacy nil-policy launches remain unchanged and unevaluated.

See [Phase 4A status](IMPLEMENTATION_STATUS_PHASE_04A.md) for exact scope, contract semantics, verification and remaining gates. Earlier Phase 4 sections below describe the original design milestone; proposed backends and positive admission remain unimplemented.

## Proposed workflow correlation and admission — Phase 4 design only

Keep per-run ingestion authoritative. Local event/run IDs remain random 128-bit lowercase hex identifiers; a future workflow uses a separate local ID. Upstream thread/item IDs are adapter-scoped observations, never global identity. A participant identifies an agent role/instance within a workflow; adapter identity identifies the parser/provider implementation and version. Neither implies model identity, which is unknown unless explicitly reported.

Membership associates runs with one primary workflow, with provenance and revision; comparison sets may reference many runs without changing membership. Existing runs remain unassigned until explicitly grouped. Parent-child execution, handoff and dependency are distinct typed relationships with source/target run references, optional supporting event IDs, source adapter/version, observation time, and origin `observed`, `user_declared` or `inferred`. Inference includes rule/version and uncertainty and is never promoted to observed. A parent is not automatically a handoff; a dependency is not a scheduler instruction. Reject self-parent and parent cycles; represent repeated handoffs as separate observations, not a forced DAG. Ambiguous/unresolved targets remain pending correlation evidence, not fake runs or dangling foreign keys.

Tool activity is a derived projection of existing tool/command events, correlated by run + adapter + observed item ID and occurrence where available. Missing IDs or conflicting reuse produce unresolved instances; never join by matching text alone. Missing starts/completions remain partial. Preserve repeated upstream observations with distinct local IDs; mark suspected duplicates in a projection using evidence, without deleting originals. A late observation during an active run gets the next sequence and retains its observed timing; terminal-run append remains forbidden. Later correlation is separately recorded with provenance, not appended to a closed history. Failed/interrupted runs remain inspectable members and cannot imply successful workflow completion.

Per-run sequence is the only guaranteed total order. UTC observation time supports display, not causality or latency across machines. A merged view may sort by `(observed_at, run_id, sequence)` with an explicit noncausal label; callers can instead inspect each run lane. Stable pages pin membership revision and a per-run high-water vector, bound run count/page size, and refresh for new members or events. Only evidence-backed edges express cross-run order. No Lamport clock or distributed transport is required for a local catalog.

A future launch follows: validate requested policy → capture platform/backend capabilities → resolve every required dimension → present effective restrictions and unknowns → bind explicit approval to immutable policy/capability/workspace/executable identities → revalidate capability freshness immediately before spawn → persist admission record → launch through approved backend. No evidence of admission means no launch. A workflow supplies defaults and a permission ceiling; each run has its own effective policy. Widening either requires a new request and approval. Capability changes invalidate previous approval rather than silently changing enforcement. Cancellation remains available during admitted work; backend failure terminates admission/execution and records uncertainty about cleanup.

Current StartSpec consent and Codex sandbox flags do not implement this resolver or durable approval record. Policy details and the platform matrix are in [security](SECURITY_MODEL.md). A branch creates files only; executing restored code is a separate future admission.

## Proposed evaluation boundary

A versioned evaluation definition names evaluator implementation/version or digest, configuration digest, test-suite and dataset versions/content digests, metric definitions/units and aggregation rules. An evaluation run freezes an evidence manifest: run IDs, event IDs and high waters plus verified payload digests, history integrity, membership revision, committed snapshot IDs/manifest hashes, and source revision only when independently recorded. A mutable workspace path, provider thread ID, or current run summary is not an immutable input. Freeze the relevant metadata and terminal outcome with provenance; later damage annotations do not rewrite the evaluated record. Partial inputs are explicit and normally ineligible for baseline comparison.

Evaluation results are separate versioned judgments: pass/fail/error/skipped/unknown, structured values with units and method, evidence references, and diagnostic omission reasons. Missing cost/tokens/quality is null with a reason, never zero. Distinguish provider-reported usage, local measured elapsed time, estimated cost with dated price/configuration provenance, and evaluator judgments. Existing timestamps can support a labeled observation interval; accurate process duration needs monotonic timing instrumentation. Existing histories provide lifecycle, sanitized events and supported snapshots, not token billing, hidden reasoning, complete source revisions or historical policy enforcement.

Regression comparisons require compatible evaluator/configuration/dataset/metric versions and comparable input scope, adapter versions, completeness and timing definitions. Otherwise return incomparable with reasons; no single invented quality score. Keep individual trials and aggregation definitions for nondeterministic evaluators. Model-based evaluation would disclose external data transfer/cost and require separate consent and policy enforcement. Even a local test suite is executable untrusted code and must pass future admission. No evaluator runs now. Evidence refs must be retained by any future retention design; missing/corrupt evidence invalidates reproducibility instead of reconstructing invented data.

## Implemented Phase 3 publication and recovery (2026-10-22)

Capture requires source-byte consent and an idle recorder. The source is the selected execution's workspace or a registered ready materialization for that execution; the caller cannot request an arbitrary restore destination. Effective exclusions include the versioned defaults, user paths and nested app-data path. Capture reserves preparing metadata, performs two 100-entry-batched traversals with per-read identity/size/mode/mtime checks, verifies matching manifests, publishes exact-byte file and manifest objects, verifies their contents, and commits references + committed metadata in one SQL transaction. A detected change fails; no automatic retry hides it. This is observed consistency, not a filesystem-atomic snapshot.

Interruption before final SQL commit leaves preparing metadata and possibly durable orphan objects. Startup marks it failed and retains files; interruption after commit retains a committed snapshot whose manifest/objects are checked again. Existing corrupt objects are never replaced. Validation failure marks a snapshot damaged; cancellation alone does not. No committed snapshot with failed object validation is usable for restore/branch. Failure recording itself can fail on an unwritable database; subsequent recovery handles remaining preparing rows.

Restore/branch validates all source objects, records a preparing materialization, exclusively creates a random-ID directory under managed-workspaces, writes private independent copies, validates actual restored entries/hashes/modes, syncs files/directories, and commits ready last. Existing destinations are refused. Failure or restart leaves failed metadata and the partial directory; no arbitrary deletion occurs. Ready workspaces may subsequently be edited, so ready denotes successful materialization, not perpetual byte identity. Subsequent capture on that workspace creates a new snapshot; unchanged bytes deduplicate, changed bytes produce new hashes. Parent/source references are immutable and point to pre-existing records, preventing cycles through supported APIs.

Operations have a nonblocking service admission gate and 10-second deadline. SQLite retains its existing bounded write gate. Host request deadlines are 120 seconds for startup hello, 30 seconds for snapshot/branch/inventory and 15 seconds otherwise. EOF/shutdown can interrupt an operation; recovery preserves committed state and fails unfinished operations. No commands execute during capture/restore, and no model automatically resumes. Inventory is non-destructive and includes retained unreferenced/temp counts; no GC or cleanup endpoint exists.

## Implemented Phase 2 flows (2026-10-22)

These flows supersede the Phase 1 staging persistence described later. Open validates private files, obtains the owner lease, configures SQLite, verifies/applies ordered migration 1, and imports legacy journals once without changing their source. The importer reads at most the legacy 32 MiB/10k-event run budget, with at most 100 directory entries per inventory batch. Database transactions make each imported run all-or-nothing. Conflicting event identities are excluded from the new index with damaged-history diagnostics; original evidence remains available.

For capture, the recorder redacts/limits a typed event, supplies the next consecutive sequence, and synchronously calls Append. The repository rejects duplicate/gapped sequences or terminal-run writes, publishes a large payload if needed, inserts the index and updates run lifecycle/sequence together, then commits. The recorder does not announce committed progress before return. Concurrent producers must retry explicit STORE_BUSY/CONFLICT responses after reading current sequence; accepted order is transaction order, never wall-clock order. Live capture has no retry queue: storage failure stops the run with an interruption annotation when writable.

Startup quick_check/foreign_key_check, sequence/lifecycle relationship checks and streaming payload verification run before capture is offered. Missing/corrupt events stay indexed for inspection, history becomes damaged, and completed metadata is projected as interrupted. On-demand detail failure also persists the damage indication where possible. Unfinished runs become interrupted with engine_restarted_process_cleanup_unverified and recovered=true in batches of 100. No lifecycle event is invented; no process is resumed or killed from stored metadata. Reopening is idempotent. Structural DB corruption fails closed with evidence preserved; automatic repair/GC is absent.

run.query pages descending by normalized UTC creation time and ID; event.query pages ascending by integer sequence with run/filter/high-water scoped opaque cursors. Metadata reflects current status while high_water/count describe the event traversal. Refresh starts a new traversal. Legacy event.list remains bounded to 100 events/512 KiB and uses SQL, not whole-journal scans. Private IPC remains request/reply; no network listener.

Phase 2/3 above supersede their storage and branch details; Phase 4 supersedes distributed-clock assumptions. Proposed Windows job objects, cleanup, durable cancellation intent and replay are not implemented.

## Event lifecycle

1. User selects owned workspace, prompt, adapter, permissions and limits; host records explicit consent tied to the run specification.
2. Host negotiates IPC. Engine validates paths/policy, obtains workspace/store leases, assigns random local run ID and persists `starting` before spawn.
3. Adapter runs Codex directly with argv (no shell interpolation); independent bounded stdout/stderr readers prevent pipe deadlocks.
4. Validate upstream record size and schema, redact at capture boundary, preserve supported unknown data, normalize envelope. Do not infer execution success from one text message.
5. Assign the next per-run sequence without a Lamport clock, then commit append-only event and run update transactionally. Blob becomes durable before its DB reference. Only acknowledged commits reach the durable timeline.
6. Readers page by ingest sequence; filters use indexed kind/run fields. UI labels missing, redacted, truncated, unsupported, and corrupt data explicitly.

P1 uses a private bounded staging JSONL journal and manifest, not a claimed durable timeline; P2 imports validated staging records transactionally and becomes the authoritative store.

## Run/process lifecycle

`created → starting → running → completed | failed | cancelled | timed_out | interrupted`. Spawn errors may transition starting → failed. Terminal states are immutable except a recovery annotation stored as a new record. A process zero exit without a completed turn or with malformed trailing data is incomplete/failure, not success. Store both OS exit reason and adapter terminal outcome. Persist cancellation intent before signaling; race resolution favors observed termination facts, with exactly one terminal record.

Rust owns Go; Go owns agent process group (POSIX) or job object (Windows). EOF/UI close cancels runs, waits a short configured grace, kills the owned tree and reaps it. P1 default proposed deadline: 120 seconds for smoke runs, 3-second graceful cancellation and 2-second forced-cleanup verification. Unsupported process containment blocks live execution on that platform. Bound output bytes, line sizes, queue size and pending IPC requests. Tool/iteration limits are enforced only where observability supports them; post-observation limits may overshoot and must be labeled. Token/cost limits cannot be hard guarantees when reported after completion.

## Recovery

At startup take exclusive writer ownership, apply migrations, verify references, mark nonterminal runs interrupted after proving no owned process remains. Never automatically resume a live model. Reconcile orphan temp blobs and completed-but-unreferenced objects after a grace window. On disk full/read-only store/queue saturation, stop recording and cancel execution; do not silently discard evidence and claim success. Checkpoint WAL only under a safe maintenance policy. Backups use SQLite backup APIs plus reachable immutable objects, not a live database file copy.

## Branching and replay

A branch references an immutable parent checkpoint and shares reachable immutable objects. Materialize into a fresh owned directory; validate snapshot completeness before publishing branch ready. Original run cannot be appended by branch operations. Replay matches captured interactions by adapter, canonical request identity, sequence and scope; unmatched requests fail closed with no implicit live fallback. State restoration is separate from replay and live reruns.

## Supervision diagnostics

No output is not proof of deadlock. Record `stalled_suspected`, deadline, repeated-tool-cycle, resource-limit, user-cancel, and engine-disconnect separately. Confirmed deadlock requires diagnostic evidence such as an observed wait-for cycle. Phase 6 adds heuristics; Phase 1 already bounds execution.

## Implemented Phase 1 lifecycle

Start validates explicit consent, absolute workspace/executable, prompt length, allowed sandbox, relative exclusions and timeout 1–3600 seconds. It creates a random 128-bit run ID and metadata, then asynchronously records created → starting, probes the CLI and scans the workspace before running. All phase-one observations use event schema v2, a single writer and a monotonic local decimal sequence. There is no Lamport counter or fabricated causality. Typed event payloads are sanitized before append/fsync, then available to the UI.

Completion requires process exit zero, a completed upstream turn, no failed turn/error, no malformed records, and a complete final metadata scan. Failure, user cancellation, deadline and engine EOF have distinct terminal states/reasons. A sink failure cancels the child and preserves partial history; if disk failure also blocks metadata, the error is surfaced while connected and recovery later marks interruption. Cancellation intent is currently in memory, not crash-durable; this differs from the future durable lifecycle design above.

The host serializes bounded RPC requests and polls pages of up to 100 events / 512 KiB. Go continues recording independently. Rust waits up to 15 seconds for a reply and marks the connection unhealthy on transport failure. EOF triggers Go cleanup; host Drop waits up to 8 seconds before killing an unresponsive engine. SIGKILL/OS crash and descendants that create a new session can escape graceful group cleanup; recovery explicitly says process cleanup is unverified. No automatic retry or model resumption occurs.

Restart takes an exclusive advisory store lock and marks nonterminal metadata interrupted; it does not kill a PID inferred from stale history. Corrupt records are skipped with warnings and a completed run with damaged history is downgraded to interrupted. A corrupt/incomplete run directory produces an interrupted summary and does not block unrelated runs; opening its details returns the error. Phase 1 scans journals to serve pages and is bounded per run; SQLite indexing/performance work is Phase 2.
