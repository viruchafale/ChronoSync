## Evidence and decision

The audit found that policy.Resolve is a pure evaluator of caller-supplied evidence, admission.Apply validates references rather than their provenance, and migration 3 replays those references rather than authenticating them. The supervisor already refuses all non-nil policy requests. Codex version probing and recording use the unchanged nil-policy legacy path. The Rust StartSpec rejects unknown fields, but Go run.start previously ignored them. React consent resets on edits but has no OS-authentication step.

Introduce a closed engine-owned ProviderRegistry in internal/policy. Production construction pins provider ID, implementation/version, interface version and exact runtime target to the compiled conservative implementation. There is no public registration, plugin loading, deserialization or fake-provider injection API. Same-package test registrations exist only in _test.go. A zero-value registry refuses. Arbitrary code executing inside the trusted engine can bypass Go package boundaries or call the pure resolver; this is a code-ownership boundary, not protection from engine compromise.

Registry.Resolve takes intent and a provider selector, never caller-supplied evidence. It validates the policy through the existing resolver, copies the request, obtains provider generation before assessment, checks returned identity/target/scope/source/generation, then rechecks generation and revocation. Resolution uses an engine-owned clock after acquisition; clock regression within the call refuses. Providers must honor the two-second context and return bounded, detached evidence. Context deadlines do not forcibly terminate malicious in-process code. Per-dimension freshness, limitations, enforcement level and exact restriction matching remain the existing resolver's responsibility. Errors expose static codes, not raw provider diagnostics. No evidence cache or transferable trusted-evidence token exists.

The only production registration wraps unchanged ConservativeProvider, which reports unknown/advisory with no verified guarantee. Its fixed generation describes only that absence of enforcement. No OS probes, backend discovery or environmental detection justify positivity. The supervisor obtains its diagnostic assessment through this registry and still unconditionally returns PolicyError before setup. Tests cannot install providers through the production constructor. Raw Resolve remains a pure domain/test API and is not a launch boundary.

Reject unknown fields and duplicate case-equivalent keys in Go IPC envelopes and run.start parameters. Retain protocol 1 and its existing fields. This closes silent fallback where a caller could send an unsupported restriction or verification flag and receive a legacy run. No approval/provider/admission method is added. Other existing query/snapshot parameter decoders are unchanged; this is not a claim that every historical IPC decoder is strict. No public contract extension is required for this rejection-only hardening.

## Approval decision and unresolved mechanism

The user explicitly selected **Require OS-backed authentication** during Phase 4E. A local intent checkbox or native dialog alone does not satisfy that requirement. No reviewed OS authentication mechanism exists in this repository. Therefore no trusted approval issuer, approval-validation producer, principal authenticator or positive admission is implemented. Existing principal IDs, evidence digests and external_validation markers remain unauthenticated model references, including after SQLite replay.

The following is a contract for a future separately approved handler, not a callable API:

- The engine allocates an unpredictable nonzero challenge ID and binds the exact canonical manifest, engine epoch, authenticated session/principal scope and engine-selected bounded expiry. SQLite's unique challenge/reference and revision constraints enforce one owner and one accepted response. Random identity is not authentication.
- A reviewed host/OS ceremony must authenticate the selected principal and bind its result to that specific challenge and manifest. Frontend intent can request the ceremony; it cannot choose authoritative actor, times, provider, effective policy or approval result. A generic successful OS prompt without transaction binding is insufficient.
- Verify fresh OS proof before recording the approval reference; serialize approval/revocation using existing repository revisions. Same operation and body return a historical receipt; a conflicting body fails. Concurrent distinct responses have one winner. A new operation cannot reuse a consumed challenge. Authentication attempt/rate-limit and proof-retention design remain unresolved.
- Any manifest change requires a new admission/challenge. Before approval, cancellation uses the domain Refuse transition; after approval use Revoke. Revocation before claim prevents readiness; racing with claim is ordered by the existing transaction, and post-claim revocation consumes the attempt and blocks final validation. No process cancellation success is inferred.
- Restart rotates the engine epoch and invalidates unclaimed approval/readiness. Reopening a stopped backup does the same. Coherent live rollback, same-user history rewriting and forged external proof are not detected by hashes or SQLite. Claims with uncertain outcomes remain consumed/unknown; no launch or PID-based cleanup occurs.

Migration 3 is adequate for the existing reference-state invariants. It does not store a reviewed authenticated principal/proof schema. If the chosen authentication mechanism needs additional durable fields, stop with a focused schema proposal; do not hide proof material in opaque strings or add migration 4 implicitly.

## Security decision register

| Decision                        | Current position                                                | Required next evidence/authorization                                                                                                                                                         |
| ------------------------------- | --------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Approval strength               | OS-backed authentication required by user; handler blocked      | Select first target OS/version and mechanism; specify principal, transaction binding, freshness, same-user attacker boundary, cancellation and recovery; approve a scoped feasibility review |
| Trusted capability registration | Closed compiled allowlist, conservative only                    | Each future provider needs reviewed code/distribution identity, exact backend context and adversarial enforcement tests; no runtime plugin registration                                      |
| Private input binding           | No raw secrets or private-input authority                       | Approve commitment threat model and key/broker lifecycle before a private-reference binding can be production-ready; low-entropy hashes are not secrecy                                      |
| Credential/key storage          | No collection, key generation, storage or new crypto dependency | Separate explicit lifecycle and access-boundary decision, including restart/key loss                                                                                                         |
| Rollback protection             | Stopped reopen invalidation only; live rollback unsupported     | Trusted external state or another reviewed mechanism before any rollback-resistance claim; no SQLite-only workaround                                                                         |
| Backend and object identity     | No positive enforcement; path/artifact hashes are insufficient  | Reviewed target backend and atomic binding/revalidation for executable, cwd, workspace and inherited resources                                                                               |
| Public approval IPC             | No operations added                                             | Separate typed contract and authenticated host/session design proposal; explicit approval before implementation                                                                              |

These decisions do not provide OS isolation, secure same-user containment, strong human presence, trusted wall time, signed distribution, race-free executable resolution or exactly-once process execution. Phase 1–3 native GUI acceptance remains open. Stop at Phase 4E's implemented refusal/registration/validation boundary and reference tests; no later work is implied.
